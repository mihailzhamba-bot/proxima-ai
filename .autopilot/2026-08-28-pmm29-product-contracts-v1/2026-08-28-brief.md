Задача PMM-29: продуктовые контракты v1 в contracts/ + codegen + контрактные тесты. Работай в режиме autopilot semi: атомарные шаги, каждый шаг проверяется, в конце отчёт.

КОНТЕКСТ РЕПО: приватная data-платформа Proxima (WB-кабинеты). Прочти AGENTS.md в корне перед стартом. Стек: Node 22 (npm workspace services/collector), Python 3.14 через uv (tools/). Команда verify: make verify (install + codegen + typecheck + test + contracts + migrations + secrets scan). Контрактные схемы в contracts/ (JSON Schema Draft 2020-12), TS-типы генерируются make codegen в services/collector/src/contracts/ - руками не редактировать (правило DEC-001). tools/verify_contracts.py итерирует contracts/*.schema.json и валидирует contracts/examples/*.synthetic.json - новые схемы подхватятся без правок кода.

ЦЕЛЬ: три новые схемы по образцу существующих (contracts/source-artifact.schema.json - структура, $id стиль https://proxima.local/contracts/<name>/v1, additive-only версионирование: новые поля опциональны, удаление/смена типа = новая мажорная версия):

1. contracts/signal.schema.json - детерминированный сигнал детектора. Поля: signal_id (uuid/строка), scenario_code (enum: SCN-001 | SCN-005 | SCN-008 - расширяемый под W2), snapshot_id (обязателен, формат как в существующих схемах - воспроизводимость), tenant_id, created_at (ISO 8601), trust_marking (enum: unreleased | released - обязательное поле), rub_assessment (объект {value_rub: number, method: enum revenue|profit} - method ОБЯЗАТЕЛЬЕН внутри объекта, защита от revenue-в-маске-profit; сам rub_assessment nullable = оценка неизвестна), source_refs (массив непустых строк-ссылок на артефакт/таблицу/дату, minItems 1), поля данных обнаружения nullable с явной unknown-семантикой (unknown = null + соседнее boolean-поле is_unknown, ноль не является unknown).

2. contracts/diagnosis.schema.json - выход LLM-диагноза (LLM НЕ генерирует числа, все цифры приходят извне): signal_id, primary_cause (строка), alternatives (массив 2-3 строк), unknowns (массив строк), source_refs (minItems 1 - каждое утверждение имеет ссылку), confidence_note (строка), reviewer (объект {verdict: enum pass|block, model: string}).

3. contracts/decision-record.schema.json - запись решения AM (append-only): signal_id, decision (enum: accepted | rejected), actor (строка), decided_at (ISO 8601), reason (nullable: обязательна при rejected - вырази через if/then на JSON Schema), expected (объект {metrics: array, horizon_days: integer > 0}), actual (nullable - null означает статус «открыто», решение ещё не проверено), delta (nullable), outcome (enum: confirmed | refuted | partial | unknown; обязательным становится только при непустом actual - вырази через if/then).

4. contracts/examples/signal.synthetic.json, diagnosis.synthetic.json, decision-record.synthetic.json - валидные примеры по образцу существующих examples. Плюс минимум 3 негативных примера (например signal-bad-nomethod.synthetic.json: rub_assessment без method; signal-bad-norefs.synthetic.json: пустой source_refs; decision-bad-reason.synthetic.json: rejected без reason) -Negative примеры должны ПАДАТЬ на tools/verify_contracts.py с указанием поля. Проверь, как существующий verify_contracts.py отличает валидные примеры от негативных (посмотри код и нейминг существующих examples) - следуй тому же механизму.

5. make codegen - TS-типы с баннером AUTO-GENERATED. 6. Контрактный тест TS по образцу services/collector/tests/intake-contract.test.ts: реальная Ajv-валидация, позитив + негатив кейсы на каждую схему.

ЗАПРЕТЫ: не трогать существующие три M1-схемы (source-artifact, acquisition-attempt, domain-release) и их examples; generated-файлы руками; секреты; Makefile (verify_contracts уже подхватывает схемы - правка не нужна, убедись только); README/docs. git add ТОЛЬКО пофайлово для своих файлов (в дереве есть чужие незакоммиченные изменения - их не трогать и не коммитить). Не мержить в main. Не выдумывать данные: в примерах синтетические значения (fixture-стиль), не реальные SKU/цены.

ГОТОВНОСТЬ: npm install в worktree перед прогоном; make codegen; make verify зелёный.
