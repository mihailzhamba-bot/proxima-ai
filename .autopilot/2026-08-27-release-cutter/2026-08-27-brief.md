# Создать в проекте Release Cutter — обязательный шлюз между планированием и Autopilot

Работай в корне текущего Git-репозитория.

Это **задача на реализацию**, а не просьба предложить концепцию. Самостоятельно исследуй проект, создай необходимые файлы, проверь их корректность и покажи итоговый diff.

Не изменяй продуктовый код проекта. В рамках этой задачи разрешено изменять только конфигурацию OpenCode, инструкции агентов, команды, скиллы и служебную документацию процесса.

## 1. Что я хочу получить

В проекте уже используются два скилла:

- `grill-me` или `grilling` — для уточнения решений и устранения неопределённости;
- `autopilot` — для выполнения уже сформулированной задачи.

Нужно добавить между ними третий слой:

```text
Grill Me
Что именно мы хотим сделать и какие решения ещё не приняты?
        ↓
Release Cutter
Нахуя это нужно? Нужно ли это сейчас? Можно ли не делать?
Можно ли переиспользовать готовое? Как получить тот же результат дешевле?
        ↓
Autopilot
Реализует только согласованный минимальный объём.
```

Название нового скилла:

```text
release-cutter
```

Название read-only субагента:

```text
release-critic
```

Release Cutter должен не просто критиковать план, а находить **самый дешёвый безопасный путь до полезного релиза**, сохраняя необходимое пользовательское поведение.

Это не «сделать максимально дёшево любой ценой». Это:

```text
минимальное время до проверяемого результата
+
минимальная сложность
+
приемлемый технический и продуктовый риск
+
возможность безопасного отката
```

## 2. Сначала исследуй текущее окружение

Не начинай с уточняющих вопросов.

Сначала самостоятельно:

1. Определи корень Git-репозитория.
2. Проверь `git status`.
3. Найди и прочитай:
   - `AGENTS.md`;
   - `CLAUDE.md`, если есть;
   - `opencode.json` и `opencode.jsonc`;
   - `.opencode/`;
   - `.claude/`;
   - `.agents/`;
   - документы с roadmap, PRD, backlog, архитектурой, ADR и release-планами.
4. Найди фактические пути и точные названия существующих скиллов:
   - `grill-me`;
   - `grilling`;
   - `autopilot`;
   - связанные с ними команды и агенты.
5. Не предполагай, что названия совпадают с указанными мной. Используй реально найденные идентификаторы.
6. Проверь установленную версию OpenCode и поддерживаемый ею формат:
   - project-local skills;
   - markdown agents;
   - markdown commands;
   - permissions;
   - вызов subagent из команды.
7. Если локальная версия отличается от текущей документации, адаптируй реализацию под установленную версию.
8. Не перезаписывай существующие скиллы, команды или агентов.
9. Все изменения делай идемпотентно: повторный запуск этой задачи не должен дублировать секции или ломать конфигурацию.

Если после исследования остаётся действительно блокирующая неопределённость, задай не более трёх конкретных вопросов. Не спрашивай то, что можно определить из репозитория, Git-истории, конфигурации или документации.

Не создавай npm-пакет, плагин, MCP-сервер, базу данных или отдельный сервис. Для этой задачи достаточно native skills, agents, commands и правил проекта.

## 4. Назначение `release-cutter`

Создай `.opencode/skills/release-cutter/SKILL.md`.

Frontmatter должен быть валидным и минимальным. Имя должно совпадать с директорией:

```yaml
---
name: release-cutter
description: Challenge the necessity, timing, scope and implementation approach of a roadmap item, then produce the cheapest safe path to a verifiable release before Autopilot starts implementation.
compatibility: opencode
metadata:
  role: release-gate
  mode: read-only-analysis
---
```

При необходимости скорректируй необязательные поля под фактически поддерживаемую версию OpenCode.

### Основная роль

Release Cutter — независимый критик плана.

Его главный вопрос:

```text
Какой минимальный объём действительно должен существовать,
чтобы мы получили проверяемый результат релиза?
```

Он должен иметь право сказать:

```text
Эта задача вообще не нужна.
```

Но любое такое решение должно быть доказано, а не основано на вкусе модели.

### Release Cutter обязан

Перед реализацией задачи:

1. Понять результат, ради которого задача существует.
2. Привязать задачу к конкретному релизному результату.
3. Проверить, действительно ли задача является блокером релиза.
4. Проверить, нужна ли она именно сейчас.
5. Проверить, существует ли более дешёвый способ получить тот же результат.
6. Найти возможности:
   - не делать;
   - отложить;
   - сделать вручную на первом этапе;
   - использовать конфигурацию вместо кода;
   - переиспользовать существующий модуль;
   - использовать уже подключённую зависимость;
   - использовать официальный API или SDK;
   - использовать готовое поддерживаемое open-source решение;
   - сделать узкий end-to-end vertical slice;
   - заменить универсальную платформу одним конкретным адаптером;
   - заменить автоматизацию полуавтоматическим процессом до подтверждения спроса.
7. Сравнить исходный вариант с минимальным безопасным вариантом.
8. Определить, что входит и не входит в текущий релиз.
9. Зафиксировать критерии приёмки.
10. Подготовить ограниченный brief для Autopilot.

## 5. Правило доказательств

Release Cutter не должен быть «генератором сомнений».

Перед выводами он обязан исследовать:

- roadmap и PRD;
- acceptance criteria;
- существующий код;
- конфигурацию;
- зависимости;
- Git-историю;
- уже существующие интеграции;
- ADR;
- открытые задачи;
- тесты;
- ограничения инфраструктуры;
- предыдущие попытки реализации;
- известные инциденты и технический долг, если данные доступны.

Для каждого существенного утверждения указывай:

```text
Evidence
Assumption
Unknown
```

Не выдавай предположение за факт.

Не используй ложную точность. Если нет данных для оценки «16 часов», используй диапазон или относительную оценку:

```text
S / M / L
или
1–2 дня / 3–5 дней / больше недели
```

Объясняй, на чём основана оценка.

## 6. Внешний поиск и GitHub

Когда задача потенциально решается готовым инструментом, библиотекой, SDK или сервисом, Release Cutter должен провести ограниченный build-vs-buy/reuse поиск.

Проверять:

- официальный ли это SDK;
- лицензия;
- активность разработки;
- дата последнего релиза;
- количество активных maintainers;
- открытые критические проблемы;
- известные security-риски;
- совместимость с текущим стеком;
- реальная стоимость интеграции;
- vendor lock-in;
- стоимость сопровождения и обновлений;
- насколько решение сокращает код именно в этом проекте.

Нельзя рекомендовать зависимость только потому, что она существует на GitHub.

Иногда 300 строк локального кода дешевле, чем тяжёлая внешняя платформа. Иногда официальный SDK дешевле собственного клиента. Release Cutter должен сравнивать **полную стоимость владения**, а не количество строк первой реализации.

При отсутствии доступа к интернету явно указывать:

```text
External reuse research: NOT VERIFIED
```

## 7. Обязательный workflow

Реализуй в скилле следующий процесс.

### Шаг 1. Определить релизный результат

Сформулировать одним предложением:

```text
После релиза пользователь/оператор сможет ________,
что даст измеримый результат ________.
```

Отдельно определить:

- целевого пользователя;
- текущее неудовлетворительное состояние;
- требуемое конечное поведение;
- критерий успеха;
- срок или релизное окно;
- ограничения;
- non-goals.

Если задача не связана ни с одним наблюдаемым результатом, это отдельный риск.

### Шаг 2. Применить пять вопросов существования

Для задачи, компонента или функции ответить:

1. Кто конкретно этим воспользуется?
2. Что сломается или останется невозможным, если этого не будет?
3. Почему это должно появиться именно сейчас?
4. Какая гипотеза или требование оправдывает существование этого элемента?
5. Сколько будет стоить не только создание, но и сохранение этого элемента?

### Шаг 3. Найти load-bearing assumptions

Выделить 3–5 ключевых предположений, без которых план теряет смысл.

Для каждого:

```text
Claim:
Fails if:
Evidence available:
Evidence missing:
Cheapest test:
Kill criterion:
```

Не составляй длинный абстрактный список рисков. Нужны только предположения, способные убить или существенно изменить решение.

### Шаг 4. Найти варианты

Всегда рассмотреть минимум три пути:

```text
A. Не делать сейчас / отложить / решить вручную.
B. Минимальный безопасный end-to-end вариант.
C. Исходный вариант из roadmap.
```

Добавить четвёртый вариант `REUSE/BUY`, если существует реалистичный готовый способ.

Для каждого пути оценить:

- пользовательскую ценность;
- время до первой проверки;
- сложность реализации;
- сложность тестирования;
- операционные затраты;
- будущую стоимость поддержки;
- зависимость от внешних систем;
- риск миграции;
- риск отката;
- необратимые решения;
- объём неизвестных.

### Шаг 5. Сократить scope

Классифицировать элементы исходного плана:

```text
CORE
Непосредственно нужен для результата релиза.

SUPPORTING
Не даёт результат сам, но необходим для безопасной работы CORE.

DEFER
Полезен, но не нужен для текущего релиза.

DROP
Не связан с подтверждённым результатом или решает гипотетическую будущую проблему.
```

Для каждого `DEFER` указывать условие возврата:

```text
Вернуть в работу, когда ________.
```

Например:

```text
Вернуть универсальную систему коннекторов,
когда появятся минимум три подтверждённых разных источника
с несовместимыми контрактами.
```

### Шаг 6. Найти минимальный vertical slice

Минимальный вариант должен проходить через необходимые слои end-to-end и быть самостоятельно проверяемым.

Плохо:

```text
Сначала создать универсальную базовую архитектуру коннекторов.
```

Хорошо:

```text
Получить один реальный отчёт Meta Ads,
преобразовать в текущий внутренний формат,
сохранить в существующую витрину,
показать оператору результат,
зафиксировать ошибку и повторный запуск.
```

Не предлагай горизонтальные технические слои, которые нельзя отдельно продемонстрировать или проверить.

### Шаг 7. Выдать вердикт

Разрешены только следующие основные вердикты:

```text
KEEP
Исходный вариант уже является минимальным безопасным путём.

REUSE
Результат можно получить через существующий код, конфигурацию,
официальный SDK, поддерживаемую библиотеку или внешний инструмент.

SHRINK
Результат сохраняется, но часть исходного scope переносится за релиз.

DEFER
Задача имеет смысл, но сейчас не является релизным блокером.

DROP
Задача не влияет на подтверждённый результат релиза.

BLOCKED
Нельзя безопасно принять решение без конкретного факта,
зависимости или бизнес-решения.
```

### Шаг 8. Определить статус передачи

Кроме вердикта всегда выдавать один handoff-status:

```text
READY_AUTO
Autopilot может начинать работу автоматически.

NEEDS_APPROVAL
Нужно решение пользователя перед реализацией.

NEEDS_INPUT
Не хватает максимум трёх блокирующих ответов.

BLOCKED
Исполнение запрещено до снятия блокировки.
```

#### `READY_AUTO` разрешён только когда

- пользовательское поведение не ухудшается;
- acceptance criteria не изменились;
- внешний контракт не меняется;
- безопасность не ослабляется;
- нет необратимой миграции данных;
- не меняется согласованный релизный результат;
- минимальный путь основан на существующих проверенных механизмах;
- rollback понятен;
- scope однозначен.

#### `NEEDS_APPROVAL` обязателен, когда меняется

- пользовательский scope;
- acceptance criteria;
- дата или состав релиза;
- публичный API;
- схема или смысл хранимых данных;
- безопасность;
- доступы;
- юридические или compliance-требования;
- платный внешний сервис;
- значимый vendor lock-in;
- необратимое решение;
- утверждённая дорожная карта.

Release Cutter может рекомендовать изменение утверждённой дорожной карты, но не должен молча её переписывать.

## 8. Что запрещено сокращать автоматически

Оптимизация scope не должна превращаться в выпуск небезопасной поделки.

Без отдельного обоснования и подтверждения нельзя вырезать:

- authentication;
- authorization;
- tenant isolation;
- input validation;
- защиту секретов;
- целостность данных;
- идемпотентность критичных операций;
- безопасные миграции;
- rollback;
- минимально необходимое логирование;
- минимально необходимую наблюдаемость;
- обработку известных failure paths;
- тесты acceptance criteria;
- юридические и compliance-требования;
- резервное копирование там, где потеря данных неприемлема.

Release Cutter ищет **самый дешёвый безопасный путь**, а не самый короткий diff.

## 10. Работа с полной дорожной картой

Если на вход передан не отдельный task, а roadmap или большой epic, Release Cutter должен перейти в batch-режим.

В batch-режиме:

1. Выделить конечный результат релиза.
2. Собрать dependency graph.
3. Найти критический путь.
4. Для каждой задачи определить: `RELEASE-BLOCKING` / `SUPPORTING` / `POST-RELEASE` / `DROP` / `NEEDS-EVIDENCE`.
5. Найти задачи, которые можно выполнять параллельно.
6. Найти преждевременные платформенные работы.
7. Найти дублирование.
8. Найти задачи, которые существуют только потому, что в плане ранее было принято слишком сложное решение.
9. Предложить: `Release 0` (минимальный безопасный проверяемый результат), `Release 1` (следующий полезный слой), `Later`, `Drop`.
10. Не запускать отдельный полный аудит каждого микротаска.
11. Один утверждённый gate для epic должен покрывать дочерние задачи, пока они не выходят за `Scope lock`.

## 11. Поведение `release-critic`

Создай `.opencode/agents/release-critic.md`.

Это должен быть `subagent` с низкой температурой и read-only permissions.

Он может: читать файлы; искать по проекту; исследовать Git-историю без изменений; читать roadmap и документацию; анализировать зависимости; при наличии разрешения выполнять web search; загружать скилл `release-cutter`; возвращать структурированный отчёт.

Он не может: менять продуктовый код; менять конфигурацию; удалять файлы; устанавливать зависимости; запускать миграции; делать commit; делать push; самостоятельно запускать Autopilot; молча утверждать изменение scope.

Предпочтительный frontmatter:

```yaml
---
description: Read-only release critic that challenges necessity, timing, scope and implementation cost before Autopilot executes roadmap work.
mode: subagent
temperature: 0.1
permission:
  edit: deny
  write: deny
  apply_patch: deny
  bash: deny
---
```

Адаптируй названия permission-полей под текущую версию OpenCode. Не используй deprecated `tools`, если текущая версия поддерживает `permission`.

Если полный запрет `bash` мешает читать безопасную Git-историю, разреши только конкретные read-only команды через granular permissions: `git status`, `git log`, `git show`, `git diff`, `git branch --show-current`, `git rev-parse`.

Запрети: `git commit`, `git push`, `git checkout`, `git switch`, `git reset`, `git clean`, `rm`, `mv`, `cp`, package installation, migration commands, deployment commands.

Если granular permissions нельзя надёжно настроить, оставь `bash: deny` и используй read/grep/glob.

## 12. Команда `/release-gate`

Создай `.opencode/commands/release-gate.md`.

Команда должна запускать `release-critic` как отдельный subtask и передавать ему `$ARGUMENTS`.

Пример вызова: `/release-gate ROADMAP-42 — добавить ежедневный импорт Meta Ads`.
Также вход в виде ссылки или пути: `/release-gate @docs/ROADMAP.md`.

Команда должна требовать: загрузить `release-cutter`; исследовать репозиторий и связанные документы; не изменять файлы; вернуть отчёт Release Gate; закончить одним из handoff-status; не запускать Autopilot.

Используй актуальный синтаксис OpenCode: `agent: release-critic`, `subtask: true`.

## 13. Команда `/release-task`

Создай `.opencode/commands/release-task.md`. Это оркестрационная команда.

Workflow: 1. Запустить release-critic. 2. Получить Release Gate. 3. Обработать handoff-status. 4. Зафиксировать утверждённый Scope lock. 5. Только после этого передать Autopilot ограниченный brief.

### При `READY_AUTO`

1. Сохранить утверждённый gate в `docs/release-gates/<date>-<slug>.md`.
2. Загрузить реально найденный скилл Autopilot.
3. Передать ему только раздел `Autopilot handoff`.
4. Явно передать: Gate ID; In scope; Explicitly out of scope; Must reuse; Must not introduce; acceptance criteria; verification; rollback; stop conditions.
5. Разрешить начать реализацию автоматически.

### При `NEEDS_APPROVAL`

1. Показать рекомендацию. 2. Показать разницу между исходным и сокращённым scope. 3. Запросить одно конкретное решение. 4. Не запускать Autopilot до ответа. 5. После подтверждения сохранить gate и продолжить с утверждённым вариантом.

### При `NEEDS_INPUT`

1. Не задавать длинное интервью самостоятельно. 2. Вызвать реально найденный `grill-me`/`grilling`. 3. Передать ему только блокирующую ветку решения. 4. Ограничить интервью вопросами, которые действительно меняют scope или архитектуру. 5. После получения ответа повторно запустить Release Gate. 6. Не уходить в бесконечный цикл. Максимум: Release Gate → Grill Me → повторный Release Gate. Если после этого решение всё ещё не определено, вернуть `BLOCKED`.

### При `BLOCKED`

Остановиться и показать: конкретную блокировку; кто или что может её снять; минимальный следующий шаг; какие задачи можно выполнять независимо от блокировки.

## 14. Scope lock для Autopilot

Autopilot не должен самостоятельно расширять утверждённый объём.

Добавь в интеграцию правила:

1. Реализуй только In scope.
2. Не реализуй Explicitly out of scope.
3. Не создавай универсализацию для будущих гипотетических сценариев.
4. Не добавляй дополнительные настройки без текущего потребителя.
5. Не вводи новую зависимость, если gate требует reuse существующего решения.
6. Не делай unrelated refactoring.
7. Не добавляй «заодно» новые функции.
8. Не меняй acceptance criteria.
9. Если обнаружена обязательная дополнительная работа, остановись.
10. Верни задачу в Release Gate с объяснением, почему Scope lock недостаточен.

Autopilot может делать локальный рефакторинг только когда он необходим для утверждённого поведения и входит в тот же тестируемый slice.

## 17. Защита от бюрократии

1. Один полный gate на epic или значимую верхнеуровневую задачу.
2. Не запускать полный gate на каждый технический подшаг.
3. Не задавать вопросы, ответы на которые есть в репозитории.
4. Не задавать больше трёх блокирующих вопросов за один проход.
5. Не создавать двадцать общих рисков.
6. Не требовать точных денежных оценок без данных.
7. Не требовать пользовательских интервью для внутренних обязательных миграций, security-работ и compliance.
8. Не оспаривать задачу ради самого оспаривания.
9. Если исходный план уже минимален и разумен, выдать `KEEP / READY_AUTO`.
10. Главный результат — ускорить безопасный релиз, а не увеличить объём документации.
