# Спецификация: PMM-20 — ядро детектора SCN-001 (падение продаж)

## Задача

AM кабинета WB замечает падение продаж постфактум: клиенты жалуются, продажи недели как падают, а никто не заметил. Нужен детерминированный детектор, который ежедневно сравнивает продажи (заказы) каждого SKU и кабинета с сезонным baseline (учёт дня недели) и выдаёт сигнал с разложением «в чём причина»: трафик, конверсия или средний чек. Источник: задача PMM-20 (Jira PMM) + решения грилля 2026-08-27 (9 веток, см. brief «Дополнения»).

## Решение

Чистое детерминированное ядро в control-plane: на вход — канонический бандл дневных метрик по SKU (без БД и сети), на выход — результат прогона: сигналы PROPOSED с декомпозицией Шепли (U×CVR×AOV), дельтами против Expected(7/14/28), ₽-дельтой, фингерпринтом canonical_hash; BLOCKED-кейсы (мало истории, плохие данные) со счётчиками. Рядом — loader: резолвит выгрузки WB из staging, парсит payload по реестру колонок (fail-closed), строит канонический бандл. Никакого LLM, всё помечено `unreleased`.

## Решения по реализации

- **Стек**: Python 3.14 (uv), `services/control-plane`; деньги и метрики в `Decimal`; канонический JSON = sorted keys + компактные сепараторы, sha256. Почему: PEP 758 импортного engine требует 3.14; Decimal — конвенция источника; детерминизм — требование AC PMM-20.
- **Метрика**: продажи = заказы (leading indicator: KPI «дни → часы»; выкупы лагируют на доставку). U = openCard, CVR = orders/openCard, AOV = ordersSumRub/orders. Выкупы — в context.
- **Baseline**: s_w = mean(день недели w за 28д, без оценочного дня) / mean(все дни за 28д); Expected(D,W) = MA(W дней до D) × s_w(D). Триггер: Actual(D)/Expected(D,28) − 1 ≤ −20% И хотя бы одно из окон 7/14 тоже ниже порога (корроборация против шумного индекса). Дефолты `default_config()` (все в конфиге): `drop_threshold=0.20`, `rub_floor=Decimal("3000")`, `cooldown_days=7`, `maturity_min_days=21`, `maturity_window_days=28`, окна `(7,14,28)`.
- **Декомпозиция**: Шепли по 3 множителям (среднее вклада по 6 порядкам подстановки), точно суммируется в revenue_delta_orders; нулевой фактор — ветка «схлопнулся» (вклад 100% схлопнувшемуся фактору при живых остальных).
- **Дедуп**: состояние дедупа — вход ядра (list открытых сигналов: level, key, opened_at, last_seen_date), персистентность — за вызывающим (daily-цикл, PMM-32). Открытый сигнал обновляет last_seen_date; новый сигнал не создаётся до восстановления: Actual(D) ≥ Expected(D,28)×(1−drop_threshold) («выше порога», как в брифе) либо истечения cooldown_days с последнего seen. Почему состояние снаружи: ядро остаётся чистым и тестируемым.
- **Хэши**: `snapshot_id` = canonical_hash входного бандла (evaluation_date + отсортированные дневные метрики панели + определение панели) — считается ядром от входа, попадает в каждый сигнал; `run_fingerprint` = canonical_hash(Scn001RunResult) — идентичность прогона целиком. `source_refs[]` = список task_id staging-выгрузок, из которых собран бандл (заполняет loader).
- **Кабинет**: зрелая панель = SKU с ≥21 из 28 дней истории; сумма дневных метрик по панели → та же математика; excluded_count/panel_size в payload. Почему панель: churn новых SKU искажал бы кабинетный baseline.
- **Loader**: разделён на чистый парсер (`parse_payload_row(payload, column_registry) -> DailyMetrics`, тестируется без БД) и тонкий резолвер DB→payload (psycopg, `DATABASE_URI`, последние DOWNLOADED task_id, покрывающие [D−28, D]). Реестр колонок — один dict; имя WB-колонки = UNKNOWN до smoke R16 (в коде — константы с комментарием «verify via smoke»).
- **Профиль отчётности**: `Scn001RunResult` = signals[] (PROPOSED, отсортированы), blocked[] (INSUFFICIENT_HISTORY/INVALID_BASELINE/INVALID_INPUT), counters (candidates, filtered_by_rub, dedup_suppressed, blocked_by_reason), run_fingerprint. Всё `unreleased`.
- **Smoke R16**: отдельный модуль `smoke.py`, read-only: берёт одну строку payload, печатает сверку ключей с реестром; без `DATABASE_URI`/туннеля печатает UNKNOWN и завершается 0. Не входит в `make verify`.
- **Jira R17**: комментарий с 9 решениями грилля + перевод в «В работе» (уже разрешено Mike выбором опции 9 в грилле).
- **Границы контрактов**: `contracts/` не трогаем (PMM-29, bot lane); DetectorResult — frozen dataclass control-plane (ноль новых зависимостей: pydantic приедет с PA-41 W1 и своим пином), выровненная по минимальному набору PMM-29 механическим маппингом позже.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `metrics` | канонические типы входа: `DailyMetrics`, `MetricBundle`, агрегация кабинетной панели | `MetricBundle.build(per_sku_rows, maturity_min_days)` | нормализацию Decimal, сортировку |
| `baseline` | сезонный индекс и Expected | `weekday_index(series)`, `expected(series, d, window)`, `history_status(series, d)` | скользящие окна, порог зрелости 21/28 |
| `decomposition` | Шепли | `decompose(u0,cvr0,aov0, u1,cvr1,aov1) -> Contributions` | 6 порядков, zero-collapse ветки |
| `signal` | триггер, ₽-фильтр, дедуп, `DetectorResult` | `detect(bundle, config, threshold_source, dedup_state, evaluation_date) -> Scn001RunResult`, `canonical_hash(obj)` | пороговую логику, сортировку, fingerprint |
| `config` | `Scn001Config` + `ThresholdSource` protocol | `GlobalThresholdSource(config)`, `default_config()` | чтение env |
| `loader` | реестр колонок, парсинг payload | `parse_payload_row(payload) -> DailyMetrics`, `load_bundle(db, d, window) -> MetricBundle` | SQL-резолв task_id, psycopg |

Швы для тестов (и идеал «один шов» соблюдён на уровне ядра): **`detect()` — единственный публичный шов ядра**; loader тестируется через `parse_payload_row` (чистая функция). SQL-слой loader'а — не шов unit-тестов (smoke накрывает его на реальных данных).
