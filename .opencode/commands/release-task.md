# /release-task

Оркестрационная команда. Workflow: 1. Запустить release-critic. 2. Получить Release Gate. 3. Обработать handoff-status. 4. Зафиксировать утверждённый Scope lock. 5. Только после этого передать Autopilot ограниченный brief.

Аргументы: `$ARGUMENTS` — задача / epic / roadmap / ключ Jira / `@файл`.

## Шаг 1. Release Gate

1. Запусти субагента `release-critic` через task tool (read-only): передай `$ARGUMENTS` и требование работать по скиллу `release-cutter`.
2. Получи отчёт Release Gate (шапка `## Gate` + 13 секций + строка `DISCOVERY_STATUS`).
3. До завершения gate ничего не строится и Autopilot не запускается.

## Шаг 2. Обработать handoff-status

### При `READY_AUTO`

1. Сохранить утверждённый gate в `docs/release-gates/<YYYY-MM-DD>-<slug>.md`; Gate ID `RG-<YYYYMMDD>-<slug>` указать в шапке.
2. Загрузить реально найденный скилл Autopilot (`~/.agents/skills/autopilot`).
3. Передать ему ТОЛЬКО раздел 12 отчёта (Autopilot handoff) — не весь отчёт.
4. Явно передать поля Scope lock: Gate ID; In scope; Explicitly out of scope; Must reuse; Must not introduce; acceptance criteria; verification; rollback; stop conditions.
5. Приложить 10 правил Scope lock (ниже) и оговорку про локальный рефакторинг.
6. Разрешить начать реализацию автоматически.

### При `NEEDS_APPROVAL`

1. Показать рекомендацию.
2. Показать разницу между исходным и сокращённым scope.
3. Запросить одно конкретное решение.
4. НЕ запускать Autopilot до ответа.
5. После подтверждения сохранить gate в `docs/release-gates/<YYYY-MM-DD>-<slug>.md` и продолжить с утверждённым вариантом (как при READY_AUTO).

### При `NEEDS_INPUT`

1. Не задавать длинное интервью самостоятельно.
2. Вызвать реальный скилл `grill-me` (`~/.claude/skills/grill-me`).
3. Передать ему только блокирующую ветку решения.
4. Ограничить интервью вопросами, которые действительно меняют scope или архитектуру (максимум три).
5. После получения ответа повторно запустить Release Gate.
6. Не уходить в бесконечный цикл: максимум один цикл Release Gate → Grill Me → повторный Release Gate. Если решение всё ещё не определено — вернуть `BLOCKED`.

### При `BLOCKED`

Остановиться и показать: конкретную блокировку; кто или что может её снять; минимальный следующий шаг; какие задачи можно выполнять независимо от блокировки.

## Scope lock для Autopilot (передавать в каждый brief)

Autopilot не расширяет утверждённый объём самостоятельно:

1. Реализуй только In scope.
2. Не реализуй Explicitly out of scope.
3. Не создавай универсализацию для будущих гипотетических сценариев.
4. Не добавляй дополнительные настройки без текущего потребителя.
5. Не вводи новую зависимость, если gate требует reuse существующего решения.
6. Не делай unrelated refactoring.
7. Не добавляй «заодно» новые функции.
8. Не меняй acceptance criteria.
9. Если обнаружена обязательная дополнительная работа, остановись.
10. Верни задачу в Release Gate с объяснением, почему Scope lock недостаточен.

Оговорка: локальный рефакторинг разрешён только когда он необходим для утверждённого поведения и входит в тот же тестируемый slice.

Дочерние задачи ссылаются на Gate ID (`RG-<YYYYMMDD>-<slug>`) в своём описании; один gate на epic покрывает дочерние задачи, пока они не выходят за Scope lock.
