Ревизия v2.1 от 08.09.2026 (v2 от 03.09 приведена к фактам недели 1 решением D33: read-only ключи WB у аналитика, зона `docs/analytics/`, реальные суммы в эталонах). Автор: John (PM). Статус: принята Mike 08.09.2026. Решения зафиксированы в `DECISIONS.md` D26 и D33.

Источники: `AGENTS.md`, `docs/agent-system/RULES.md`, `docs/agent-system/TOOLS.md`, `docs/governance/dod-checklist.md`, `docs/state/WORKS-TODAY.md`, PRD v2.2 и `epics.md` (Epic 6), `ARCHITECTURE-SPINE.md` (AD-1..AD-18).

## 1. Кто это и чего он не делает

Владислав - второй человек в проекте: аналитик, который **независимо пересчитывает всё, что насчитали агенты**, и разработчик, который пишет модули в закреплённых за ним зонах. Занятость - полный день, 30-40 часов в неделю; планируемый темп - 3-4 единицы работы в неделю. У него есть собственный проект того же типа (аналитика кабинета WB, выстроенная как борды); код оттуда в проект не переносится - берутся только идеи, и реализуются заново в наших контрактах (D26).

Чего он **не** делает: не принимает продуктовых решений и не закрывает открытые вопросы OQ (это Mike, D1); не мержит PR и не деплоит (D3, D7); не выпускает токены сам; живые вызовы WB API - только выданными Mike read-only ключами (02.09, PMM-58, D33), сырые ответы хранит локально под NDA и никуда не выкладывает; ничего не пишет на сервер; не правит существующие верификаторы `tools/verify_*.py`, миграции, сгенерированные контракты и замороженные зоны.

Что он делает: **теневой пересчёт цепочки** (§2), сверку с кабинетом (§3.1), разметку ретро-тревог (§3.2), приёмку историй по критериям (§3.3), ревью требований и данных (§3.4), и пишет код в своих зонах (§5).

Единственное право, которого нет больше ни у кого, кроме Mike и агента-ревьюера: **остановить релиз** (§4).

## 2. Главное: теневой пересчёт цепочки

### 2.1 Принцип

Владислав считает те же числа **своим кодом на своём стеке**, не переиспользуя наши функции. Вход - только исходные данные: обезличенные фикстуры репозитория, полные фикстуры с VPS, после релиза - боевая база на чтение. Выход - числа по каждому шагу; они кладутся в репозиторий как **эталон** и становятся единственным источником ожидаемых значений для нашего гейта.

Смысл именно в независимости: если считать нашими же функциями, повторится наша же ошибка. Поэтому наш код он читает только после того, как получил своё число, и только чтобы объяснить расхождение.

### 2.3 Эталон и гейт

Эталон - данные, не код: `verification/golden/<шаг>-<дата>.json`. Формат полей взят из существующего каркаса `services/control-plane/tests/evals/reference/` (`calculation_id`, `formula_version`, `expected_value`, `source_ref_ids`) и из `contracts/source-artifact.schema.json` (провенанс):

```json
{
  "schema_version": 1,
  "calculation_id": "norm-2026-08-29",
  "formula_version": "median-14d-v1",
  "computed_by": "vladislav",
  "computed_at": "2026-09-05T10:00:00Z",
  "method": "медиана 14 календарных дней [eval-14, eval-1]; при чётном n - среднее двух средних",
  "source": { "kind": "synthetic|fixture|artifact", "sha256": "…", "path": "…" },
  "tenant_id": "amirova-test",
  "expected": { "norm": { "orders": "34.50", "revenue": "34595.00" } },
  "tolerance": { "orders": "0.01", "revenue": "0.01", "deviation_pct": "0.05" }
}
```

Деньги - строкой с двумя знаками (AD-10). Гейт `tools/verify_shadow.py` читает каталог, пересчитывает наш результат на том же входе и падает с перечислением расхождений; цель `shadow` добавляется в зависимости `verify` в `Makefile`. Правок CI не требуется: `.github/workflows/verify.yml` уже запускает `make verify` целиком. Гейт делается **файловым, а не через базу**: `make pg-roundtrip` без локального PostgreSQL 16 печатает `SKIP` и выходит с кодом 0, то есть любой гейт, завязанный на базу, молча пропускался бы.

### 2.4 Ограничение, из-за которого меняется порядок работ

Деньги в обезличенных фикстурах репозитория умножены на **секретный** коэффициент 0.8-1.2 (`tools/anonymize_fixture.py`, соль вне git) и строки прорежены до 200 КБ. Пересчитать по ним `700 860 ₽` нельзя в принципе. Поэтому:

1. Сначала эталоны на **синтетике**, которая уже задана в критериях приёмки: норма 34.5 / 34 595 ₽, факт 27 / 41 141 ₽, отклонение −21.7 % / +18.9 %. Они не зависят от ограничения и закрываются гейтом сразу.
2. Числа W10/W35 - на **полных фикстурах** с VPS, локальным прогоном (переменная окружения включает полные фикстуры), плюс как условие приёмки релиза 1.14 на боевых данных.
3. Реальные дневные суммы кабинета в эталонах (28 значений окна нормы и W10/W35) **допустимы** - решение Mike 08.09 (D33); полные фикстуры по-прежнему вне git.

### 2.5 Четыре конвенции, которые фиксируются до первого прогона

Без них два корректных кода дадут разные числа в последнем знаке, и каждое расхождение придётся разбирать вручную:

1. Медиана при чётном числе точек: среднее двух средних (значение 34.5 это подразумевает, но правило нигде не записано).
2. Округление денег: `34 595.00` против `34 595.01` - правило округления половины.
3. Округление `deviation_pct` до 0.1 процентного пункта и момент округления (до или после деления).
4. Нумерация недель для W10/W35: стандарт ISO-8601 и год отсчёта.

Владислав предлагает формулировки в первую неделю, Mike утверждает, John вносит в контракты `norm` и `brief` (Story 2.2) и в PRD (OQ-18).

## 4. Право «нет»

Расхождение теневого пересчёта или сверки с кабинетом, выходящее за допуск и не объяснённое, **блокирует релиз**. Механика: Владислав заводит задачу в Jira с меткой блокера, пишет строку в журнал и сообщает Mike и John в тот же день. Релиз не выпускается, пока расхождение не закрыто одним из трёх способов: исправлен наш код; исправлен его пересчёт; Mike снимает блокировку записью в `DECISIONS.md` с причиной.

До выяснения правильным считается **его число**: он считает от исходных данных, наш код - через несколько слоёв преобразований.

Та же формулировка стоит в критериях приёмки Story 2.6, в PRD §15 и в D26 - при правке менять во всех четырёх местах.

## 5. Свои зоны кода и разделение с конвейером

Правило проекта - один пишущий на дерево, поэтому зоны разведены явно.

**Зоны Владислава** (агенты их не трогают): `verification/` (эталоны), `tools/verify_shadow.py` и его собственные инструменты (`tools/retro_alarms.py`, скрипты теневого пересчёта), журналы `docs/state/{CABINET,SHADOW}-RECONCILIATION.md`, `RETRO-ALARM-LABELS.md`, `SM3-BASELINE.md`, его отчёты в `docs/analytics/` (маркировка `unreleased`, суррогатные ключи), и истории Epic 6.

**Берёт поштучно** (каждая - своя ветка и PR, по очереди с агентами): октябрьские истории Epic 4 и Epic 5, экраны веб-морды (там, где нет замороженной auth-зоны), модули M-06+ после D-решения по кандидатам.

**Не берёт**: критический путь сентября (истории 1.4-1.14, 2.3-2.6, 3.1) и единицы с пометкой `[Claude]` (живые вызовы и запись на сервер) - до гейта 30.09.

Процесс тот же, что у агентов: ветка `feat|fix|docs|chore/*` от `origin/main` → PR → агент-ревьюер → `make verify` зелёный → приёмка Mike одним действием. Новые файлы верификаторов создавать можно (например `tools/verify_shadow.py`); **существующие `tools/verify_*.py` не правит** - гейт, который он мог бы ослабить, должен меняться чужими руками.

### 6.2 Доступ к боевой базе на чтение: сегодня его выдать нечем

Проверено 03.09: на боевой базе схема версии 6, RLS выключен (ноль политик), из ролей `proxima%` существуют только `proxima` (владелец, superuser), `proxima_dev` и `proxima_diagnostics`. Единственный существующий read-only путь - роль `proxima_diagnostics` через обёртку, требующую root, то есть выдать её человеку значит выдать сервер целиком.

Поэтому доступ появляется отдельной единицей (Story 6.4): собственная LOGIN-роль аналитика по образцу `infra/bootstrap/provision-postgres-diagnostics.sh` (`NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS`, `default_transaction_read_only = on`, таймауты `statement`/`lock`/`idle_in_transaction`, `GRANT CONNECT` + `USAGE` + `SELECT ON ALL TABLES` + `ALTER DEFAULT PRIVILEGES`), URI-файл `/etc/proxima-ai/secrets/<роль>_uri` с правами `0600`, запись процедуры в `docs/operations/`. Состав грантов предлагает `bmad-architecture`, выдаёт Mike, значение URI передаётся вне чата.

Порядок работы после выдачи:

```bash
ssh -N proxima-db                      # держать открытым; снимать только ssh -O cancel
export DATABASE_URI="$(< путь_к_uri)"  # значение не эхоить
psql "$DATABASE_URI" -c "SELECT …"
```

После миграции 011, когда включится RLS, первым statement сессии обязателен `SELECT set_config('proxima.tenant_id', 'amirova-test', false)` - третий аргумент `false` (сессия, не транзакция). Как отличить причины пустого ответа: `permission denied` - нет гранта; ноль строк на непустой таблице - GUC не установлен; проверка `SELECT current_setting('proxima.tenant_id', true)`.

### 6.3 Фикстуры: где проходит опасная граница

Токены лежат **на один уровень выше** фикстур, поэтому копируется только подкаталог:

```bash
# безопасно (без 409 МБ финансового отчёта):
scp -r proxima:signal-inputs/fixtures/wb-api/statistics/supplier-orders ./fixtures/
scp -r proxima:signal-inputs/fixtures/wb-api/statistics/supplier-sales  ./fixtures/
scp -r proxima:signal-inputs/fixtures/wb-api/analytics                  ./fixtures/
```

Копировать `~/signal-inputs/` целиком или `signal-inputs/*` **нельзя**: на этом уровне лежат файлы токенов WB и Telegram и посторонние данные. Полные фикстуры в git не попадают (каталог в `.gitignore`); в репозиторий идёт только обезличенное до 200 КБ через `tools/anonymize_fixture.py`.

### 6.4 Чего не даём

Роль-владельца базы и её URI; пароль диагностической роли; URI песочницы (она про тестовую базу); токены WB сверх выданных read-only (§6.1), токен Telegram, ключ бэкапа, ключи объектного хранилища; sudo на сервере; права записи где-либо на сервере; ssh-доступ к серверу (до отдельного решения Mike).
