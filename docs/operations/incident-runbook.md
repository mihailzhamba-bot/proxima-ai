# Инцидент-runbook

Что делать, когда что-то пошло не так. Все команды первого шага - только чтение. Решение о деплое, откате и ротации принимает владелец проекта. Обновлено 03.09.2026.

Общее правило: сначала выяснить состояние по реестру прогонов, потом смотреть логи, и только потом что-то менять. Каждый разобранный случай записывается: строка в `docs/state/WORKS-TODAY.md`, если появилась воспроизводимая проверка, и запись решения в `DECISIONS.md`, если менялось правило.

## 1. Утром нет сводки

Признак: экран показывает предупреждение вместо цифр либо данные вчерашние.

```bash
ssh proxima 'systemctl list-timers proxima-morning@*.timer --no-pager'
ssh proxima 'systemctl status proxima-morning@amirova-test.service --no-pager | head -20'
ssh proxima 'journalctl -u proxima-morning@amirova-test.service --since "06:00" --no-pager | tail -40'
```

Затем реестр: последний прогон, его статус и шаг, на котором остановился.

Дальше по причине: таймер не сработал - проверить, что юнит включён и что сервер не перезагружался; прогон упал на сборе - смотреть ошибку WB (пункт 4); прогон упал на норме - проверить, хватает ли полных дней; прогон успешен, а экран пустой - смотреть режим витрины и подключение веб-морды.

Не чинить на боевом «на живую»: если сводка не пришла на следующее утро после релиза, действие по умолчанию - откат на предыдущий тег, а не правка.

## 2. Пришёл алерт

Сообщение из служебного канала означает падение юнита. Порядок тот же, что в пункте 1, начиная с журнала конкретного юнита. Важное: алерт не содержит причины, он лишь маркер - причина всегда в журнале и реестре.

## 3. Алерта нет, но что-то сломалось

Ожидаемая ситуация: канал доставки - одна попытка без повторов по прибитому адресу. Проверка живости канала:

```bash
ssh proxima 'systemctl status proxima-alert@.service --no-pager | head -10'
ssh proxima 'grep -n api.telegram.org /etc/hosts'
```

Если адрес сервиса изменился, сообщение не уйдёт молча. Это известная слабость, задача на повторные попытки заведена. До её закрытия дежурная проверка - реестр прогонов каждое утро, а не ожидание сообщения.

## 4. WB отдаёт ошибку или лимит

Признак: прогон сбора упал, в журнале код 429 или иной отказ.

Порядок: посмотреть заголовки ответа в реестре артефактов (там сохранены заголовки и статус) - лимиты приходят именно оттуда; сверить с зафиксированными лимитами в `docs/state/API-FACTS.md`; убедиться, что не запущены два прогона одновременно.

Правило проекта: замеренный лимит важнее лимита из спецификации. Если замер разошёлся с документацией - запись в `API-FACTS.md` с датой, а не молчаливая правка кода.

Живой вызов WB для диагностики делается только с сервера и только по явному разрешению владельца; ответ сразу сохраняется в фикстуру.

## 5. Цифры разошлись с кабинетом

Признак: строка сводки не совпала с кабинетом при сверке.

Порядок: определить, на каком шаге расходится - для этого существует независимый пересчёт (`docs/agent-system/roles/analyst-vladislav.md`, журнал `docs/state/SHADOW-RECONCILIATION.md`); проверить, что сверяется закрытый день, а не свежий - поздние отмены переписывают день до двух недель; проверить статус данных и полноту дней окна нормы.

**Расхождение выше допуска блокирует релиз** до объяснения; снять блокировку может только владелец записью в журнале решений.

## 6. Подозрение на утечку токена

Немедленно: считать токен скомпрометированным, не выяснять «точно ли».

Порядок: перевыпустить токен в личном кабинете WB и отозвать старый; положить новое значение в каталог секретов на сервере с прежними правами; перезапустить контейнеры, которые его читают; проверить, что старое значение нигде не осталось - в переменных окружения, локальных копиях, истории команд; просканировать репозиторий и историю; записать инцидент с датой, что именно утекло и что сделано.

Известный открытый случай: токен аналитики боевого кабинета используется неизвестным потребителем вне сервера. Он переквалифицирован из вопроса квоты в инцидент с учётными данными, ротация запланирована до первой единицы работы с воронкой.

## 7. Откат релиза

Условия отката записаны до начала релиза, в плане отката. Порядок: вернуться на предыдущий тег; удалить прогоны релиза по идентификатору (транзитивно); при необходимости перевести витрину в режим демо-данных. Миграции не откатываются - компенсируются следующей.

Инструмент удаления прогона пишется историей 1.7; до его появления откат данных выполняется вручную под наблюдением владельца.

## Чего в этом документе намеренно нет

Порогов эскалации, дежурства и целевых уровней доступности: продукт обслуживает одного пользователя, дежурство - он сам. Когда появится второй кабинет, сюда добавляется раздел «кого будить».
