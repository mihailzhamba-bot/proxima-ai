# 0005. Staging за SSH-туннелем, loopback-only

## Контекст

Mike смотрит кабинет с разных машин, не только с Mac mini. Домен не передан, публичный деплой отложен в PA-49 сессию 2. На VPS уже отработан паттерн PA-13: git bundle, detached checkout, docker build.

## Решение

Webapp поднят на VPS как контейнер proxima-webapp-staging: publish только на 127.0.0.1:3000, restart: unless-stopped, fixtures-режим без БД и секретов (WEBAPP_REQUIRE_AUTH=false). Доступ с машины Mike через SSH-туннель (алиас proxima-app, -L 3000:localhost:3000). Порты 80/443 и домен не открываются.

## Почему

Публичный URL отвергнут: домена нет, а выставлять fixtures-каркас без авторизации в интернет бессмысленно и опасно. Локальный dev на Mac mini как единственный способ просмотра отвергнут: не закрывает потребность «с любой машины каждый день» и зависит от запущенного терминала. Push в registry и CI/CD отвергнуты как лишняя инфраструктура: пересборка на VPS из git bundle уже даёт рабочий цикл обновлений. Туннель закрывает потребность без новой поверхности атаки.

## Последствия

Кабинет нельзя показать, просто отправив ссылку: у получателя должны быть SSH-ключ proxima-admin и поднятый туннель. Пока нет CI/CD, обновление staging это ручной runbook (bundle, build, restart). Диагностика «кабинет не открывается» всегда начинается с вопроса, жив ли туннель, а не только контейнер. WEBAPP_REQUIRE_AUTH=false допустим ровно потому, что порт смотрит в loopback: при переходе к публичному URL (сессия 2) возврат авторизации это первое обязательное действие.
