# ADR-0001: Налоговые режимы юрлиц в формуле contribution (tax_regime)

- Номер: ADR-0001
- Дата драфта: 2026-08-17
- Статус: **Draft** (в `Accepted` - после инвентаризации юрлиц и подтверждения ставок бухгалтером)
- Jira: PMM-2 (SPIKE, WBS AIOS-FIN-001); блокирует PMM-22 / AIOS-DEC-003 (profit-часть ₽-оценки сигналов)
- Регистрация: DEC-007 в `docs/agent-system/DECISIONS.md`

## 1. Контекст

Портфель Proxima: 4+ юрлица со смешанными налоговыми режимами (источник: вход от Mike в описании Jira PMM-2, 2026-08-17; точное число и состав - UNKNOWN до инвентаризации п. 5). Формула contribution принципиально различается: при УСН «доходы» расходы не уменьшают налог, при УСН Д-Р - уменьшают по закрытому перечню, при ОСНО добавляется НДС и налог на прибыль. Записать `tax_regime: mixed` и идти дальше = отложить решение до момента, когда юнит-экономика уже написана под один сценарий (находка Mike 2026-08-17). Вся profit-логика M2/W2+ и ₽-оценка сигналов не строятся на угаданном режиме.

С 2025 года УСН-плательщики становятся плательщиками НДС при доходе свыше 60 млн руб/год, поэтому «режим» и «НДС» - два независимых измерения: `tax_regime` не определяет `vat_status` автоматически.

## 2. Decision

`tax_regime` - enum-атрибут `legal_entity` в канонической модели, не ветка расчёта и не свойство кабинета/SKU:

```
legal_entity:
  id                        # обезличенный идентификатор
  display_name              # человекочитаемое имя
  tax_regime:               # usn_income | usn_income_expenses | osno | unknown
  vat_status:               # none | reduced_5 | reduced_7 | standard_20 | unknown
  insurance_credit_kind:    # employer | sole_proprietor | unknown (лимит вычета взносов)

cabinet_wb:
  legal_entity_id           # каждый кабинет WB закреплён ровно за одним юрлицом
```

Правила:

1. Расчёт contribution по кабинету выбирает формулу по `tax_regime` юрлица этого кабинета.
2. Дефолт для нового юрлица: `unknown`. Значения `mixed` в enum нет и быть не может: смешанность живёт на уровне портфеля (несколько юрлиц), а не внутри одного юрлица.
3. `tax_regime = unknown` -> profit-оценка = `UNKNOWN` (fail-closed, показать пустое значение, а не ноль). Revenue-оценка (PMM-22 v1) от режима не зависит и работает всегда.
4. До принятия этого ADR любое появление `tax_regime` в конфигах/модели W1 имеет значение `unknown` (не mixed) - интерим-правило из scope PMM-2; существующего артефакта со значением `mixed` в репо нет (проверено grep 2026-08-17).

## 3. Формулы contribution

Общий принцип: contribution - управленческая метрика для продуктовых решений (₽-оценка сигналов, приоритизация), не налоговая декларация. Налог входит как оценка по режиму; финальные цифры налога - бухгалтерия/1С. Все ставки - параметры с дефолтами из НК РФ на 2026-08-17, каждый дефолт помечен `[подтвердить бухгалтером]`.

### 3.0 Режимонезависимая база

```
gross_paid       = выручка по выкупленным заказам за период (кассовый метод: деньги от WB)
wb_deductions    = комиссия WB + логистика + хранение + штрафы + платная приёмка
cogs             = себестоимость проданных единиц
ads              = реклама (внутренняя WB + внешняя)
returns_cost     = стоимость обработки возвратов (логистика возврата и т.п.)

contribution_pre_tax = gross_paid - wb_deductions - cogs - ads - returns_cost
```

Термин `gross_paid`, а не `revenue`: считаем по выкупам, не по заказам - невыкупы в выручку не входят.

### 3.1 УСН «Доходы» (usn_income)

Налог не зависит от расходов. Расходы влияют только на contribution_pre_tax, не на налог.

```
tax_base_usn_d  = gross_paid                         [Q1: при договоре комиссии с WB -
                                                      вся выручка или за вычетом комиссии WB]

tax             = max(rate_usn_d * tax_base_usn_d - insurance_credit, 0)

insurance_credit = min(страховые_взносы_уплаченные + больничные_за_первые_3_дня,
                      0.5 * rate_usn_d * tax_base_usn_d)      # для employer (ООО/ИП с работниками)
                                                               # sole_proprietor: без лимита 50% [подтвердить]

rate_usn_d      = 0.06  (регион может снижать; дефолт 0.06)   [подтвердить бухгалтером]

contribution_post_tax = contribution_pre_tax - tax
```

Маржинальная налоговая ставка на +1 руб выручки: `rate_usn_d` (взносы квази-фиксированы, с выручкой не растут). Это число использует ₽-оценка сигналов (п. 4).

### 3.2 УСН «Доходы минус расходы» (usn_income_expenses)

```
recognized_expenses = подмножество (wb_deductions, cogs, ads, insurance), где каждая статья
                      соответствует закрытому перечню ст. 346.16 НК и оплачена (кассовый метод)
                      [перечень признаваемых статей подтвердить бухгалтером]

tax_base_dr     = gross_paid - recognized_expenses
tax_regular     = rate_usn_dr * max(tax_base_dr, 0)
tax_minimal     = rate_usn_min * gross_paid            # минимальный налог
tax             = max(tax_regular, tax_minimal)         # разница tax_minimal - tax_regular
                                                        # включается в расходы следующего года

rate_usn_dr     = 0.15  (регион может снижать)          [подтвердить]
rate_usn_min    = 0.01                                  [подтвердить]

contribution_post_tax = contribution_pre_tax - tax
```

Признаваемость по статьям (ожидание, проверить): комиссия/логистика/хранение WB - да; реклама - да; COGS - при оплате поставщику; взносы - да.

### 3.3 ОСНО (osno)

Два налога: НДС и налог на прибыль. База налога на прибыли - метод начисления, НДС - по счетам-фактурам; для управленческой метрики допускаем кассовое приближение с пометкой.

```
# НДС
vat_out = vat_rate / (1 + vat_rate) * gross_paid       # НДС внутри выручки
vat_in  = входящий НДС на закупки с правом вычета       # COGS-закупки, реклама, комиссия WB
                                                         # (счёт-фактура от WB) [подтвердить]
vat_due = vat_out - vat_in                              # при праве на вычет
                                                         # reduced_5: без вычета, vat_due = vat_out

# Налог на прибыль
profit_base = income_accrual - expenses_accrual - vat_due   # НДС в базу не входит
                  # допущение: income_accrual, expenses_accrual - валовые суммы, включающие НДС;
                  # вычитание vat_due переводит базу в без-НДС вид (иначе задвоение вычета)
profit_tax  = rate_profit * max(profit_base, 0)

rate_profit = 0.25  (с 2025)                            [подтвердить]
vat_rate    = по vat_status: standard_20 -> 0.20; reduced_7 -> 0.07; reduced_5 -> 0.05

contribution_post_tax = contribution_pre_tax - vat_due - profit_tax
```

### 3.4 УСН + НДС (vat_status != none при tax_regime usn_*)

С 2025: доход свыше 60 млн руб/год делает УСН-щика плательщиком НДС. Тогда к формуле 3.1/3.2 добавляется `vat_due` по правилам 3.3 (5% - без вычета до 250 млн, 7% - с вычетом до 450 млн, свыше - 20% с вычетом) `[ставки и пороги подтвердить бухгалтером]`. База УСН при совмещении с НДС переопределяется: доходы считаются без НДС (`tax_base_usn = gross_paid - vat_out`) `[подтвердить бухгалтером - входит в Q3]`:

```
contribution_post_tax = contribution_pre_tax - tax_usn - vat_due
```

Именно поэтому `vat_status` - отдельный атрибут: он может меняться при переходе порога выручки без смены `tax_regime`.

## 4. Участие в ₽-оценке сигналов (PMM-22 / AIOS-DEC-003)

Сигналы оценивают эффект управленческого решения в рублях (стоимость молчания). Налог входит как маржинальная ставка по юрлицу кабинета, не как полный налоговый расчёт per-SKU (налог считается на уровне юрлица за период):

```
impact_profit = impact_contribution_pre_tax * (1 - marginal_tax_rate)

marginal_tax_rate(legal_entity):
  usn_income            -> rate_usn_d
  usn_income_expenses   -> rate_usn_dr  (приближение: при изменении и доходов, и расходов;
                                         точнее - max(tax_regular, tax_minimal) на дельтах)
  osno                  -> vat не зависит от решения (в цене), прибыль: rate_profit
  unknown               -> impact_profit = UNKNOWN
```

При `vat_status != none` у УСН: НДС с выручки масштабируется вместе с выручкой, для решений, не меняющих валовую выручку, поправка НДС ~0 - уточняется при реализации PMM-22 v2.

## 6. Элиминация внутренних перепродаж - вне scope

Если юрлица портфеля продают друг другу товар, консолидированный P&L портфеля требует элиминации внутригрупповых оборотов (иначе COGS/выручка задваиваются). Это отдельная задача финансового контура за пределами W1-среза; данный ADR фиксирует ограничение:

- Все формулы этого ADR считаются per-legal_entity, без консолидации.
- Флаг «есть внутренние перепродажи» собирается в инвентаризации (п. 5) как вход в будущую задачу элиминации.
- Daily Brief W1 показывает метрики кабинета/юрлица, не консолидированного портфеля.

## 7. Revisit-условия

ADR пересматривается, если:

1. Юрлицо меняет режим (уведомление в ФНС до 31 декабря, действует с нового года - проверять фактическое применение, не только уведомление).
2. Добавляется новое юрлицо или кабинет перепривязывается к другому юрлицу.
3. Юрлицо переходит порог 60 млн руб/год (УСН -> НДС) или пороги 250/450 млн внутри НДС-шкалы - `vat_status` обновляется без нового ADR, если формула не меняется.
4. Меняются ставки/правила НК (бюджетные изменения, региональные льготы).
5. Меняется договорная модель с WB (комиссия <-> поставка) - перевзвешивает Q1.

## 9. Последствия

- PMM-22: revenue v1 реализуется сразу (режим не нужен); profit v2 - после Accepted и заполнения п. 5.
- Каноническая модель (PMM-29 контракты): сущность `legal_entity` с атрибутами из п. 2 попадает в контракты W2, для W1 достаточно справочника в конфиге расчёта.
- Реестр допущений (PMM-9): вместо `tax UNKNOWN` - ссылка на этот ADR с перечнем Q1-Q4.
- Risk register (PMM-10): риск «tax UNKNOWN» митигируется этим ADR (Draft) и закрывается при Accepted.
