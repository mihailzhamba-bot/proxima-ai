Подготовка образов на Harper
1. Запустить prepare_upstream.py с --destination build/upstream и фактическим
   --harper-hostname. Он проверяет hostname и exact commit из versions.lock.json,
   не перезаписывает существующие каталоги. Paperclip: release v2026.831.1,
   commit 65ec059bde30d98c92165b24a30a540800dd1f6f. Hermes: release v2026.9.11,
   commit 939e45c91d751fadd94dcd1b873ac3cb44846213.
2. Собирать Dockerfile.paperclip и Dockerfile.hermes-overlay с корнем репозитория
   в качестве context. Их отдельные .dockerignore включают build/upstream и нужные
   Markdown/HTML assets, исключают .git и runtime secrets. Общий .dockerignore
   производственных образов PROXIMA менять не требуется.
3. Paperclip использует Node 24.11.0 и pnpm9.15.4. Hermes - Python 3.12 и закреплённые
   extras sms/mcp. Образы upstream с root-entrypoint не используются.
4. Собрать Dockerfile.bridge и расширение доверенного verifier через
   Dockerfile.verification. Записать полученные registry digests в versions.lock.json
   и deployment environment. Сборки на LOOP-control не выполняются.
5. Отдельно проверить доставку образов в выбранный приватный registry. Digest образа
   в локальном registry Harper сам по себе не подтверждает доступ нового VPS.

Новый управляющий VPS
После создания VPS и разрешения deploy оператор устанавливает Docker, ограничивает
SSH/admin ingress утверждёнными адресами и создаёт отдельные каталоги /etc/loop,
служебные учётные записи и новые volumes. Через compose публикуются только локальные
127.0.0.1:3100 и 127.0.0.1:18770; PostgreSQL не публикует host port. Между серверами
используется HTTPS/проверенная приватная сеть. Реальный ingress принимается отдельно.

prepare_credentials.py создаёт только новые локальные capability keys. Файлы mode0600:
Paperclip работает как UID 1000, Hermes UID 10000, Bridge/Telegram UID 10001. PostgreSQL
получает секреты с владельцем UID его фактического образа. Каждый сервис монтирует
только нужные файлы. bridge_director и hermes_bridge_director - разные файлы для
разных UID, содержащие один Director credential. Ключи Board, runner, OpenHands,
GitHub и operator в Hermes не монтируются. Provider/Board/GitHub/Telegram credentials
выдаёт оператор отдельно; генератор не создаёт авторизацию во внешних сервисах.

Compose задаёт отдельные лимиты памяти/CPU/PIDs: PostgreSQL 1GiB/0.5/128,
Paperclip 2GiB/1.5/256, Hermes 2GiB/1/128, Bridge 256MiB/0.5/64,
Telegram 128MiB/0.25/32. Все Docker logs ротируются: local, 10MB x3.
Bridge запрещает новый dispatch при свободном месте менее 512MiB в его volume.
Достаточность стартового VPS проверяется на реальных управляющих задачах.

PostgreSQL и персональный доступ
Собственный PostgreSQL 16.6 хранится в отдельном volume. 10-paperclip-role.sh создаёт
paperclip_runtime без superuser/CREATEROLE/CREATEDB. DATABASE_URL в приватном
paperclip.env указывает на postgres:5432/paperclip с этой ролью. Пароли admin и runtime
раздельны. Paperclip HOME/PAPERCLIP_HOME: /paperclip; PAPERCLIP_CONFIG:
/paperclip/instances/default/config.json. Используется отдельный persistent volume.

Webapp первого кабинета работает в WEBAPP_DATA_MODE=postgres; WEBAPP_TENANT_ID выбирает
кабинет. Нужны WEBAPP_DATA_DATABASE_URI_FILE, WEBAPP_LOOP_DATABASE_URI_FILE,
WEBAPP_AUTH_DATABASE_URI_FILE, BETTER_AUTH_SECRET и BETTER_AUTH_URL. Отдельные DB login
roles наследуют proxima_auth_writer и proxima_loop_writer. Миграции 019-021 additive:
схема auth/queue, native BetterAuth issuer, read-only role proxima_loop_context.
Исходные имена auth user/session/account/verification сохранены. Read-only осмотр
13.09.2026 не обнаружил auth-таблиц в live/rehearsal DB; production migration не выполнялась.

Оператор создаёт личные аккаунты, регистрирует workflow_runs command='provision'
и явно добавляет cabinet_memberships: Mike как owner, конкретные сотрудники как employee.
Регистрация аккаунта не выдаёт membership. Сервер проверяет настоящую BetterAuth-сессию,
её срок и активное членство на каждом запросе. Сотрудник видит только свои задачи.
Подтверждение решения Mike и создание задачи атомарны; повтор возвращает прежнюю задачу.

Для read-only контекста Director задать WEBAPP_LOOP_CONTEXT_DATABASE_URI_FILE и
WEBAPP_LOOP_CONTEXT_TOKEN_FILE; соответствующий webapp_context secret получает только
Bridge. /api/loop/context выбирает кабинет из server config, не из запроса клиента.
Текст записей и evidence остаётся недоверенными данными, а не инструкциями для Director.

Paperclip и Hermes
В Paperclip создать одного Director с официальным hermes_gateway и конфигом
paperclip-director.example.json. Поле apiBaseUrl указывает на Bridge /hermes.
dangerouslyAllowInsecureRemoteHttp относится только к http://bridge:18770 внутри
Docker-сети одного сервера; внешний HTTP этим флагом не разрешается. Gateway key
выдаётся через secret store. Routines задаются только в Paperclip; интервал 900 секунд
является стартовой настройкой, а не измеренным SLA.

Hermes получает новый HERMES_HOME, отдельный API_SERVER_KEY и provider environment
в director.env. Использовать hermes.example.yaml: platform api_server с toolset loop
и stdio MCP /opt/loop/director_tool.py. Проверить фактический deferred tool catalog:
только loop_read_context и loop_propose_job за штатными метаинструментами Hermes.
Terminal/process/cron/browser/delegation не должны появляться в доступном каталоге.
Один /health или список /v1/toolsets этой проверки не заменяет. Telegram polling
существующего Hermes не включается. Paperclip - единственный планировщик Director.

Harper и OpenHands
Установить bridge.py, runner.py, publication.py, push_gate.py, loopctl.py и verify_candidate.py
вместе в /opt/loop на Harper; worker_dispatch.py - на Claudette. Trusted configs,
templates, prompt_file, reviewer и исходные fixtures хранятся вне worker checkout.
Проверить SSH aliases loop-worker/github-loop, отдельные служебные ключи и known_hosts.
Личные приватные ключи Mac на серверы не переносятся; ForwardAgent отключён.
Runner получает свой Bridge credential; worker/model не получают runner/Git credentials.

Service UID/GID Harper должен совпадать с UID 1000 verification image, либо образ
собирается под выбранный отдельный service UID. Каталоги не делаются world-writable.
Шаблоны изначально пусты; оператор задаёт только проверенные base_sha,
allowed_paths и prompt_file. reviewer_command - доверенный абсолютный executable
вне candidate workspace; его ответ относится к точному SHA и не содержит пропусков.
Self-report OpenHands не считается результатом проверки.

loop-runner.service запускает runner.py --config <trusted file> --serve на Harper.
Он потребляет утверждённые задания, не планирует Director. Для одного задания:
runner.py --config <trusted file> --job <job ID>. Bridge допускает одну тяжёлую работу;
неопределённая работа требует сверки до следующего dispatch.

Проверка кандидата и публикация
Порядок: prepare, immutable verify, immutable build, independent review,
begin-publication, gated push, finish-publication. Кандидат проверяется по blob каждого
tracked-файла и точному SHA; source и .git монтируются read-only. Изменения защищённых
tests/config/контрактов в worker-кандидате запрещены. Mountpoints создаются заранее;
tracked coverage, symlink, выход за checkout и неожиданные файлы отклоняются.

Producer использует только доверенные /opt/offline/npm и /opt/offline/uv, копирует их
в writable /tmp и явно запрещает сеть/download Python. Python 3.14 заранее установлен
в verification image. HOME - scratch; USER/LOGNAME берутся из фактического UID.
Prepare устанавливает locked dependencies, затем package-файлы становятся read-only.
Отдельно доступны writable build outputs, .vite-temp/.vite caches и build-only overlay
next-env.d.ts. PROXIMA_VERIFY_READONLY включает сравнение codegen без записи исходников.
make verify обязан пройти настоящий pg-roundtrip: PASS. Логи и SHA-bound receipts
сохраняются вне candidate mounts в приватном evidence directory с редактированием секретов.

Push запускается через доверенный Python -I -S wrapper. Родитель сохраняет PID/start,
PGID/SID/boot ID и release intent с fsync до отправки разрешающего байта. Если родитель
падает раньше, EOF запрещает exec. Дочерний процесс начинает новую session; recovery
проверяет всех её живых участников, включая SSH/helper после смерти лидера Git.
GIT_SSH_COMMAND отключает ControlMaster/ControlPersist. Timeout сигналит owned group;
оставшийся участник session не даёт подтвердить остановку.

Управление и восстановление
loopctl.py поддерживает status/wake/pause/resume/stop/events/recover-pr и явную сверку.
Wake идёт через Paperclip. Повтор и потеря ответа не создают вторую работу.
Неопределённый dispatch не повторяется даже после истечения 24h native idempotency Hermes.
Оператор сверяет remote run list и принимает подтверждённый external ID.
Hermes после restart переводит незавершённый run в interrupted; SSE не имеет replay,
поэтому состояние читается polling. Cursor событий Paperclip хранится постоянно.

Pause сохраняет queued job и уже выданный publication permit для продолжения после
resume. Отмена немедленно меняет generation и запрещает новые публикации. Paperclip
cancel требует Board и сам не останавливает Hermes: Bridge отдельно останавливает
Hermes и ставит OpenHands на паузу, затем проверяет их состояния. Пока подтверждения
нет или publisher может работать, отображается CANCELLING, а не подтверждённая остановка.
Поздний child отменённого parent не получает lease. Подтверждённо отозванный или аварийно завершённый
parent переводит ещё не отправленную работу в quarantine.

Потерянный worker receipt: python3 /opt/loop/loopctl.py --config <operator-config>
recover-worker --id <job> --input-file <receipt>
проверяет известный OpenHands CID и продолжает сбор bundle без второго dispatch.
Проверки ancestry/SHA/paths остаются обязательными. Перед публикацией повторно читается
Paperclip, включая отмену напрямую в upstream.

Потерянный push: runner.py --config <file> --recover-push <private publisher.json>.
Journal evidence/<job>/<attempt>/publisher.json имеет mode0600 и содержит permit;
не включать его содержимое в логи, prompts или PR. Живой процесс/session запрещает
settlement. Старый неполный journal без доказательства no-exec остаётся UNKNOWN.
Finished journal повторяет сохранённый receipt; умерший незавершённый publisher
фиксирует unknown outcome, после чего нужна внешняя сверка.

Оператор: loopctl.py --config <file> settle-publication --id <job>
--evidence-ref <inspection reference>. Проверяются destination branch SHA и все
подходящие PR. Эта операция не создаёт PR, не повторяет push и не удаляет branch.
Иной SHA или недоступная проверка оставляют permit активным. recover-pr принимает
только существующий PR с точным SHA и также требует доказанной остановки publisher.

Telegram и модели
Новый отдельный Telegram bot запускается только с заполненными allowlists user IDs
и chat IDs. Update ID/cursor записываются до обработки; свободный текст не выдаёт
разрешения. delivery_unknown и execution_unknown различаются; потерянный ответ
sendMessage не вызывает слепую повторную отправку. Для точно отклонённого update:
telegram.py --config <file> --retry-update <ID>; сохраняется исходный idempotency key.
JsonHTTP принимает uncertain:false только от настроенного trusted Bridge, включая
известный 503 до dispatch. Vendor5xx остаётся неопределённым исходом.

Для выбора Director настроить минимум две отдельно авторизованные модели в
director-eval.config.example.json. Запуск на Harper: evaluate_director.py --config
<file> --cases infra/loop-control/director-eval-cases.json --output <report.json>.
Проверяются цель, источники, неопределённость, выбор исполнителя, подтверждение Mike
и публикация. В native request передаётся нужная модель. Requested identity и
наблюдаемая identity раздельны; status.model=hermes-agent не доказывает provider/model.
Отсутствующий usage остаётся UNKNOWN. Числа вне точных SourceRef и повторение одного
факта не получают полный grounding score. Пустой config не запускает оценивание.

Backup, rollback и приёмка
Перед deploy сохранить mode0600 зашифрованные backups PostgreSQL, Bridge SQLite,
отдельного Hermes state и Paperclip storage. SQLite копируется через backup API,
не cp работающего файла; Bridge использует DELETE journal. Перед rollback прекратить
новый dispatch, остановить активные попытки и сохранить unknown intents. Восстановить
совместимые версии/schema в отдельном volume; проверить integrity и число записей.
Не удалять решения и uncertain runs ради разблокировки очереди.

Выполнение задачи подтверждает сотрудник с evidence. Mike отдельно сверяет эффект
после горизонта наблюдения. Сравниваются orders/revenue того же SKU; неподдержанный
category target остаётся unknown. Достижение цели не доказывает причинность действия.

Отдельные приёмки: код/PR; управляющий стенд на новом VPS; ежедневная работа кабинета.
Для live-стенда ещё нужны новый VPS, credentials и model selection, registry delivery,
private ingress, membership, реальный маршрут Paperclip/Hermes/OpenHands/Harper/PR,
отмена/restart и restore backup. Unit/DB/browser и component smoke не заменяют эту
сквозную приёмку. Merge и production deploy остаются решением Mike.
