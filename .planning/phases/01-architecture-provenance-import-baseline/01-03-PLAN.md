# Plan 01-03 - Linear rebaseline and Phase 1 evidence gate

## Objective

Create a new explicit Linear hierarchy for the 8-phase repository roadmap without modifying the 123 legacy issues, then close Phase 1 only against real commit, verification and independent-review evidence.

## Tasks

1. Read and record the legacy issue count and immutable as-of timestamp. Discover exact ZM workspace/team/state/project IDs; do not infer names or use `--current`.
2. Create one M1 parent issue and 8 ordered child phase issues using stable `write-id` values. Bodies contain repository phase contract links/paths, owned requirement IDs, dependencies and GO gates. Do not update, reparent, relabel or close any pre-existing issue.
3. Export only the new issue IDs, URLs, parent links and creation timestamps into `LINEAR-REBASELINE.json`. Re-read Linear and prove legacy count/IDs/state fields were not changed by this workflow.
4. For Plans 01-01 and 01-02, run `make verify` at their exact clean commit and obtain an independent cross-model deep review. Record real locators and classifications in `REVIEWS.md`; unresolved blocker or warning prevents Phase 1 completion.
5. Run final `make verify`, obtain independent review for the Phase 1 aggregate diff, and record source pre/post fingerprints, commit SHAs, command exit codes, CI locator/status and Linear IDs in `EVIDENCE.md`. Unknown or unavailable external evidence remains `pending`, never `passed`.
6. Only when every Phase 1 gate passes, mark Phase 1 requirements and roadmap status complete and advance STATE to Phase 2. Otherwise leave Phase 1 in progress with the exact blocker.

## Must haves

- Legacy Linear issue IDs and fields remain unchanged; only the new rebaseline hierarchy is written.
- Evidence contains real SHAs, timestamps and locators; no invented CI or review status.
- Every Phase 1 implementation slice has independent review `0 blocker / 0 warning` for the exact commit.
- Phase 1 does not become complete while any gate is pending.

## Immutable Linear snapshot contract

Before the first write, paginate all 123 legacy issues and store a canonical SHA-256 over sorted records containing `id`, `identifier`, `parent.id`, `state.id`, `project.id`, `priority`, `assignee.id`, `labels[].id`, `archivedAt`, `canceledAt`, `completedAt`, `createdAt`, and `updatedAt`. After creating only the 9 new rebaseline issues, recompute the hash from the exact before-ID set while excluding `updatedAt` only if Linear itself changes it without a field mutation; any other mismatch is a blocker and must be investigated before another write. Store the before ID set, both hashes, pagination cursors and raw read locators, but no issue body from untrusted legacy content.
