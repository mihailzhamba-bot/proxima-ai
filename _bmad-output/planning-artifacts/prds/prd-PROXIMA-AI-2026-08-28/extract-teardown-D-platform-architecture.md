## 2. Платформенные карточки P1–P6 — факты (§1–9)

README о слое в целом: «Известен в основном из политики конфиденциальности и оферты: на продуктовых страницах этих сущностей нет.»

### 2.1 P1 — Авторизация и профиль (`/login`)

- Назначение (§1): «Два независимых способа аутентификации: Telegram и email.»
- Сценарий (§2). Telegram: сервис получает `id`, `username`, `chat_id`; из Mini App передаётся `initData`; подтягиваются имя и фото (при наличии). Email: ввод адреса → одноразовый код через SMTP-провайдера → код проверяется, «на стороне сервиса он хранится в виде хеша» → «наблюдался переход по ссылке вида `/login?token=<64 hex>` — то есть подтверждение приходит ссылкой, а не только цифрами».
- Экран `/login` (§3): способ входа через Telegram, через Email, ссылки на условия и политику, базовые инструкции.
- Входные данные (§4): `id`, `username`, `chat_id` (Telegram); `initData` (Mini App); email (пользователь); одноразовый код (сервис → SMTP → пользователь); `token` (64 hex, в ссылке `/login?token=`); имя, фото (Telegram).
- Хранимые атрибуты профиля (§6): «имя, фото, настройки аккаунта, привязки к workspace и тарифу».
- Механика (§7): коды хранятся в виде хеша; «`chat_id` фиксируется на этапе авторизации — тот же идентификатор нужен модулю 04 для отправки алертов о смене фото в Telegram»; данные учётной записи хранятся «в течение действия аккаунта и 12 месяцев после его удаления».
- Ограничения (§8): «Способов входа два, пароля нет ни в одном»; TTL magic-link и 2FA — PENDING (см. раздел 3).

### 2.2 P2 — Workspace, тарифы и командный доступ (публичных страниц нет)

- Назначение (§1): «Контейнер, к которому привязаны пользователь, кабинеты и тариф. Раздаёт доступ к кабинетам между людьми в команде.»
- Сценарий (§2): профиль имеет «привязки к workspace и тарифу»; к workspace подключаются кабинеты WB и Ozon; другим людям выдаётся доступ уровня «просмотр» или «редактор»; пользователь видит свои кабинеты и те, к которым ему выдали доступ; лента заказов и тепловая карта учитывают этот доступ.
- Экраны (§3): заявлено «командный доступ и несколько кабинетов», переключение между кабинетами, просмотр заказов «по собственным и командным кабинетам». Сами экраны — PENDING.
- Источники сущностей (§4): Workspace и привязка к тарифу — `/privacy`; роли «просмотр» и «редактор» — `/vozmozhnosti/lenta-zakazov-wb`.
- Хранимые атрибуты (§6): «состав кабинетов, состав участников, роли, текущий тариф».
- Механика (§7): «Тариф считается **за кабинет**, а не за пользователя: обе платные позиции на `/pricing` указаны как „990 ₽/месяц за кабинет“»; «Ролей на текущий момент известно две: „просмотр“ и „редактор“. Владелец как отдельная роль не упоминается»; цитата вендора: «Лента и тепловая карта учитывают командный доступ: видны и ваши кабинеты, и те, к которым вам выдали доступ „просмотр“ или „редактор“».

Ozon: ЛК → Настройки → API-ключи → `Client-Id` и `Api-Key`. Далее: «Вносит себестоимость на странице **„Источник данных“**», «Задаёт помесячные ставки налога», «Первичная загрузка истории занимает несколько минут; данные появляются через час».

## 5. Что это означает для PROXIMA (оценка)

Опорные факты о PROXIMA, по которым оценивается применимость (контекст задачи и `AGENTS.md`): приватная multi-tenant платформа агентства (цепочка Mike → операции → менеджеры); один VPS, PostgreSQL 16, tenant = кабинет с RLS; WB-токены только на сервере (`/etc/proxima-ai/secrets/`, 0600); auth-зона заморожена до октября, затем auth/роли; утренняя сводка по кабинету; WB API только READ, split-токен с read-only битом на категорию, новый эндпоинт — сначала в allowlist; каждая запись помечена `run_id`, идемпотентна и обратима по `run_id`; каждая цифра с источником; подключение второго кабинета = строка в `tenants` + токены + экземпляр таймера. Из `.memlog.md` (записи 02.09): Telegram FR-23 и скрейпинг — Non-Goals; PMM-21 — COGS только по топ-SKU, CSV-конфиг; статусы `stale/insufficient/blocked`, таймер 05:30 (G-5); «второй tenant после M-03» (G-8).

### 5.1 Паттерны платформенного слоя, полезные для multi-tenant агентской платформы

1. **Кабинет как единица тарификации и доступа** (ARCH §8, P2 §7, P4 §1). Факт rmagent: подписка считается за кабинет; доступ раздаётся людям поверх кабинетов; workspace — контейнер «пользователь + кабинеты + тариф». Для PROXIMA: tenant = кабинет — уже совпадает; onboarding «строка в `tenants` + токены + таймер» — это и есть кабинет как единица конфигурации. Биллинговой оси у PROXIMA нет (приватная платформа), но вторая ось — «кто видит какой кабинет» — понадобится в октябре: роль назначается на пару (пользователь, tenant), RLS остаётся границей данных. Ярлык: **взять** (совпадает), ось доступа — **адаптировать**.
2. **Роли «просмотр» / «редактор»** (P2 §2, §7). Факт: две роли, владелец не упоминается, доступ распространяется на данные ленты и тепловой карты. Для PROXIMA действий с внешними последствиями нет (READ-only), поэтому «редактор» сводится к ручным вводам (себестоимость, налог, пороги, план поставок) и к подтверждению/отклонению сигналов в сводке; цепочка Mike → операции → менеджеры требует минимум трёх уровней (владелец всех кабинетов, операции — все кабинеты, менеджер — свои). rmagent даёт только форму «две роли на кабинет»; перечень прав и охват модулей — PENDING. Ярлык: **адаптировать**.
3. **Раздельные ключи по категориям как минимальные права** (ARCH §4, P3 §2, §7). Факт: три ключа WB по назначению, вендор требует заводить их отдельно, ключи «не пересекаются». Для PROXIMA это уже принцип split-токена с read-only битом; отличие — у rmagent ключи разделены по контурам, два из которых пишут (отзывы, чат), у PROXIMA — по категориям чтения. Полезная деталь — жизненный цикл: токены «удаляются при отключении кабинета» (ENT §7) — зеркало onboarding'а: offboarding tenant = удалить токены из `/etc/proxima-ai/secrets/` + остановить таймер + данные удаляемы по `run_id`. Ярлык: **взять** (модель прав), **адаптировать** (offboarding как обратная процедура).
4. **Режимы синхронизации по типу данных** (ARCH §3). Факт: шесть периодов от ~10 минут до часа и пользовательский интервал; «данные появляются через час». Урок для PROXIMA (с оговоркой, что рассогласование — реконструкция автора, раздел 4.1): утренняя сводка должна быть одним снимком одного `run_id` — все цифры одного запуска, иначе цифры разделов не сойдутся. Разные периоды допустимы позже только с меткой «на момент HH:MM» на каждой цифре (правило «каждая цифра с источником»). До M-03 — один суточный цикл (таймер 05:30). Реальные периоды rmagent — только с маркетинговых страниц в пересказе WebFetch; проверка — PENDING HAR. Ярлык: **адаптировать**.
5. **Курсор событий для лент** (ARCH §3: чат, Ozon). Факт: курсор упомянут для потоков изменений, для срезов — периодическая перевычитка (последнее — вывод автора). Для PROXIMA применимо на ступенях с лентами (заказы/продажи по `dateFrom`, курсор `rrdid` у отчёта реализации — см. `extract-drops-C6.md` §2); для суточных срезов — перевычитка по `run_id`. Механика курсора у rmagent невидима без HAR. Ярлык: **адаптировать (позже)**.
6. **Себестоимость и помесячный налог как ручные вводы с ретроспективой** (P3 §2, §4, §6; ENT §4). Факт: отдельная страница «Источник данных»; себестоимость по товарам; ставка налога хранится по месяцам. Реконструкция автора: помесячность = пересчёт прошлых периодов. Для PROXIMA: ручные вводы — отдельный слой с источником «ручной ввод, кто, когда» и периодом действия (effective month), чтобы прошлые сводки оставались воспроизводимыми (обратимость по `run_id` + «каждая цифра с источником»); совместимо с PMM-21 (COGS топ-SKU, CSV-конфиг). Формат ввода у rmagent — PENDING. Ярлык: **адаптировать**.
7. **Статус подключения и первый цикл** (P3 §2 п.7, §6 «статус подключения»). Факт: первичная загрузка «несколько минут», данные «через час»; хранится статус подключения. Для PROXIMA: явный статус tenant «ключ принят → первичная загрузка → первый успешный run» ложится на статусы `stale/insufficient/blocked` (G-5). Поведение при истечении ключа и недостаточных правах — PENDING. Ярлык: **адаптировать**.
8. **Слой пользовательского контента отдельно от данных маркетплейса, с единым сроком хранения** (P6 §1, §7; ENT §4, §7). Принцип разделения «пришло из API» vs «создано/введено пользователем» — **взять** (для ручных вводов, порогов, паспортов клиентов). Содержимое слоя у rmagent (шаблоны и черновики автоответов) — **нет** (WRITE).
9. **Журналы запросов к API** (ENT §6). Факт: политика перечисляет «журналы запросов к API» в технических данных; трактовка «логи обращений к маркетплейсам для контроля квот» — интерпретация автора. Для PROXIMA журнал вызовов WB по `run_id` (эндпоинт, время, код ответа, квота) — естественное продолжение правила `run_id` и allowlist. Ярлык: **адаптировать**.
10. **Беспарольный вход** (P1). Факт: Telegram и email с одноразовым кодом/magic-link, коды хранятся хешем, пароля нет. Для auth в октябре email magic-link — минимальная поверхность для нескольких пользователей приватной платформы; Telegram как несущая конструкция — нет (FR-23 в Non-Goals, K4). TTL токена и 2FA — PENDING. Ярлык: **адаптировать**.
11. **Справка за логином по подключению/токенам/лимитам** (P5 §7). Для PROXIMA — не продуктовый раздел, а чеклист onboarding второго кабинета в репо-доках (категории токена, read-only бит, какой ключ что питает, allowlist). Ярлык: **адаптировать (как документ)**.
12. **Сроки хранения по категориям** (ARCH §7, ENT §7). У PROXIMA политика хранения данных tenant/журналов в предоставленном контексте не описана — `UNKNOWN`; факт rmagent даёт форму записи (аккаунт, журналы, токены — три разных срока). Ярлык: **адаптировать**.
13. **`localStorage` для локальных настроек интерфейса** (ARCH §1, P6 §7). Для webapp — допустимо для фильтров/периода сводки, не для данных. Ярлык: нейтрально (MAY).

### 5.2 Что противоречит правилам PROXIMA

- **WRITE от имени пользователя.** ARCH §5: «Wildberries API — чтение и публикация от имени пользователя»; P4 §3: «AI генерирует и публикует ответы на отзывы»; ключи «Отзывы и вопросы» и «Чат с покупателями» питают модули публикации (ARCH §4). PROXIMA: WB API только READ, мутирующая операция — архитектурное нарушение (`AGENTS.md`, «Жёсткие запреты» п.2). Следствие: два из трёх ключей rmagent PROXIMA не нужны вовсе; роль «редактор» в её rmagent-смысле (если включает публикацию — PENDING) не переносится.
- **ПДн покупателей во внешний ИИ за пределами РФ.** ARCH §5–6: тексты отзывов, вопросов и чатов уходят в «OpenAI и иные провайдеры ИИ», за пределы РФ; раскрыто только в политике, модель не названа. PROXIMA: данные кабинета живут на одном VPS, токены только на сервере, секреты не попадают в промпты (`AGENTS.md`), метрики считает детерминированный код, LLM объясняет. Передача клиентских текстов и ПДн покупателей во внешний контур в правилах PROXIMA не предусмотрена; если объяснение сводки будет внешним LLM — это отдельное архитектурное решение с явным перечнем передаваемых полей (без ПДн и токенов). Это моя рекомендация, не факт.
- **Контур B — парсинг каталога и CDN по чужим артикулам** (ARCH §2). PROXIMA: скрейпинг — Non-Goal (`.memlog.md`, C4/C7), браузерная автоматизация в runtime запрещена (`tools/verify_runtime_boundary.py`), новые источники — только через allowlist. Не переносится.
- **Биллинг и оферта** (ЮKassa, договор с момента оплаты, обязательства только на оплаченный период, без SLA). У приватной PROXIMA оси биллинга нет — противоречия нет, но и переноса нет; факты — только для позиционирования (раздел 6).
- **Telegram как несущая конструкция** (факты ARCH §5: авторизация, Mini App, алерты, бот поддержки; вывод — P1 §10). Для PROXIMA — вне периметра: FR-23 в Non-Goals до появления источника (K4).
