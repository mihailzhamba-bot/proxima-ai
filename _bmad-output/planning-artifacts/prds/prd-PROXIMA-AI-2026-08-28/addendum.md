# Addendum к PRD PROXIMA AI v2

Приложение хранит то, что не должно раздувать PRD, но нужно downstream-работам: тексты отложенных требований v1, механику и отвергнутые альтернативы, рассмотренные варианты решений, карты соответствия и выжимки методик из наработок. Аудит и переопределения решений здесь не живут - они в `.memlog.md`.

Обновлено: 2026-09-02. Ревизия PRD: v2.1.

## A.1 Отложенные требования v1 (тексты дословно, PRD v1 от 28.08.2026)

ID сохранены; в PRD v2 они стоят в §4.E со ссылкой на кандидата CM-n.

### FR-2: Маршрутизация по Ярусам
Система направляет Карточку в Ярус алерта или Ярус расследования по Порогу ярусов.

**Consequences (testable):**
- Оценка 1-10 вычисляется системой для каждой Карточки; в значения входят деньги под риском и трудозатраты на исполнение.
- Порог - конфигурируемое значение по умолчанию; `[ASSUMPTION]` стартовое значение и калибровка - Open Question OQ-1.
- AM не может вручную перевести Карточку из Яруса алерта в Ярус расследования в v1 `[NON-GOAL for MVP]`; ручной вызов расследования - кандидат W2.

### FR-3: Квота сигналов
Система ограничивает поток: до 10 Сигналов в день на кабинет (PRODUCT-VISION, Продукт v0).

**Consequences (testable):**
- При превышении квоты низшие по Оценке Сигналы не показываются в инбоксе и помечаются отклонёнными по квоте с записью в Decision Memory.

### FR-10: Прогноз обнуления
Система считает прогнозную дату обнуления по остаткам FBO+FBS+свой склад и среднедневным продажам (окно 14 дней для WB).

**Consequences (testable):**
- Окно скорости продаж - 14 дней для WB (30 дней для Ozon - вне W1, Policy Layer хранит как внешний ориентир).
- Сезонность дня недели применяется к ряду продаж `[ASSUMPTION: сезонная коррекция продаж в W1 ограничена днём недели]`.

### FR-11: Два сигнала
Система порождает независимые OOS Alert и Procurement Alert по условиям из Glossary.

**Consequences (testable):**
- OOS Alert: прогноз обнуления на маркетплейсе раньше ближайшей подтверждённой поставки.
- Procurement Alert: Точка заказа пройдена, а подтверждённой поставки, закрывающей разрыв до исчерпания общего запаса, нет.
- Сигналы независимы: возможен один без другого; оба попадают в инбокс отдельными Карточками.

### FR-13: Источник данных о поставках
Система получает даты и объёмы подтверждённых поставок из источников W1.

**Consequences (testable):**
- Источник поставок в пути в W1 не закрыт; до закрытия все SCN-005 Карточки живут в режиме UNKNOWN с явным перечнем пробелов.
- Open Question OQ-2 `[NOTE FOR PM]`: без решения Procurement Alert не срабатывает никогда - только OOS Alert в UNKNOWN-режиме.

*Примечание v2:* OQ-2 закрыт 28.08.2026 (memlog v1): фаза A - ручной ввод AM плановых поставок по паттерну `products.csv`, контракт `contracts/supply-plan.schema.json` (поля `supply_id`, `tenant_id`, `nm_id`, `quantity`, `order_date`, `expected_arrival_date`, `status`, `entered_by`, `entered_at`; миграция `010_client_passport_supply_plan.sql`, PR #33); фаза B - спайк WB Supplies API (PMM-36: `factDate`, `acceptedQuantity`, lead time по реальным парам; токен категории «Поставки»). Ресёрч 28.08: факт приёмки в API есть только post-factum, до приёмки - только плановая дата продавца. XLSX-вариант вычеркнут 25.08.

### FR-17: История кабинета
AM видит историю решений кабинета с фильтром по типу Сигнала и статусу решения.

**Consequences (testable):**
- Фильтры: тип Сигнала (SCN-008/001/005), статус: открыто (до прогона Verification), подтвердилось, не подтвердилось, частично, UNKNOWN.

### FR-19: Калибровка оценок
Расхождения исходов пересчитывают confidence-фактор детектора и уточняют ₽-оценки влияния его Сигналов.

**Consequences (testable):**
- После каждого исхода confidence-фактор детектора обновляется по истории исходов в Decision Memory; формула пересчёта - OQ-6.
- Обновлённый confidence входит в ось «уверенность системы» и в Оценку 1-10.
- Калибровка правил Policy Layer исходами verification - вне W1 (Non-Goals, кандидат W2).

### FR-23: Telegram critical
Critical-Сигналы дублируются в Telegram.

**Consequences (testable):**
- В Telegram уходит только класс critical; обычные Сигналы не доставляются в Telegram.

### FR-24: Верхняя полоса и зоны экрана
Система отображает верхнюю полосу инбокса: GYR-индикацию кабинета, счётчик открытых решений, суммарные деньги под риском; Карточки разделяются на зону «дайджест» (Ярус алерта) и зону «critical» (Ярус расследования).

**Consequences (testable):**
- Счётчик равен числу Карточек в статусе «открыто».
- Суммарные деньги под риском равны сумме поля «деньги под риском» открытых Карточек; UNKNOWN-значения в сумме не участвуют и помечаются отдельно.

### Анатомия Карточки v1 (вход для AC Story 5.2)
8 полей: что произошло; данные обнаружения; деньги под риском; вероятная причина; рекомендация; запреты; подтверждение; срок и метрики проверки. Полная спецификация и demo-примеры - бриф `brief-PROXIMA-AI-2026-08-28/addendum.md`, разделы 2-3. Правила v1: карточка без поля «деньги под риском» или без SourceRef не публикуется (fail-closed); поле «запреты» присутствует всегда («запретов нет» - явно); для качества данных ₽-оценка = UNKNOWN допустима.

## A.2 Норма: отвергнутые альтернативы (D21, 30.08.2026; API-FACTS §E)

Показанный ряд кабинета Амировой (артефакт «Ряд продаж Амировой», данные фикстур 30.08):

| Альтернатива | Почему отклонена |
|---|---|
| Среднее 7 дней | Прыгает ±10 % от недели к неделе - ложные тревоги |
| «Тот же день недели за 4 недели» | 4 точки с разбросом 15..67 заказов |
| Среднее 28 дней | Захватывает июль и завышает норму после августовского спада (−36 %) |
| Медиана того же дня недели за 8-12 недель (API-FACTS §E, вариант 3) | В ряду эффекта дня недели нет: разброс внутри одного дня недели 25-47 % шире разницы между днями ~20 % |
| Норма по финотчётам (API-FACTS §E, вариант 2) | Недельный разрез и лаг 1-8 дней - «минус 23 % против обычного вторника» не строится |
| Норма по воронке (API-FACTS §E, вариант 1) | К 30.09 базы нормы по воронке не будет ни из одного источника (v3 - 7 дней; CSV копится с 01.09) |

Принято: медиана 14 последних полных дней по кабинету целиком; метрика тревоги - заказы без отмен (CV 0.32, меньше шума); выручка (finishedPrice) справочно; медиана не сдвигается единичными днями на 57-67 заказов и неполным последним днём. Окно исключает оцениваемый день (AD-8; подтверждено D22).

## A.3 Механика v1, вынесенная из PRD

- **Baseline v1 (снят D21):** скользящее окно из {7, 14, 28} дней, «самое длинное с полной историей»; при истории короче 7 дней сигнал не строится; день недели из исторического ряда; праздники не учитываются.
- **Декомпозиция v1 (UNKNOWN в v2):** выручка = U × CVR × AOV (Rakuten R-Karte), ведущий множитель; требует показов - в v3 их нет.
- **OOS-логика v1 (CM-1):** Точка заказа = полный Lead time (производство + доставка + приёмка) + Страховой запас, в днях покрытия; demo 60 + 15 = 75 дней; два независимых сигнала (OOS Alert - товар закончится на маркетплейсе раньше ближайшей подтверждённой поставки; Procurement Alert - Точка заказа пройдена, поставки, закрывающей разрыв, нет); окно скорости продаж 14 дней WB (30 дней Ozon - внешний ориентир); без Lead time / дат поставок - UNKNOWN. Формулировка demo-вывода 28.08: «15 дней = отклонение остатка от точки заказа (75 − 60), при немедленном заказе рыночного дефицита нет, каждый день промедления = день дефицита» (подтверждено Mike).
- **Policy Layer v1 (FR-20/21):** правила с 5 полями метаданных; W1-значения 60/75/120/30 дней, 100+ дней неликвид - «внешний ориентир» с дисклеймером (прислано Mike 28.08, оригиналы не найдены, даты неизвестны, клиентом не подтверждено); Lead time нормативы «от ~60 дней производство в Китае до 4 месяцев сложный товар».
- **Оси сортировки и Оценка 1-10 v1 (CM-3):** оси - влияние на прибыль (= деньги под риском), срочность, стоимость выполнения, уверенность системы, риск бездействия; оси 2-5 на стартовых эвристиках до OQ-6; Оценка 1-10 = деньги под риском + трудозатраты; порог ярусов - одно конфигурируемое значение (OQ-1).
- **Verification v1 (FR-18):** N = 7 дней для аномалий продаж и OOS; «частично» = 30-70 % ожидаемого эффекта (< 30 % - не подтвердилось, > 70 % - подтвердилось); калибровка вместе с N - OQ-3.
- **Daily-цикл v1 (снят AD-6):** данные daily к 07:00 MSK, бриф 07-08 MSK, Telegram только critical; в v2 - таймер 05:30 МСК, один юнит, Telegram = монитор.

## A.9 Best practices зарубежных аналогов - расширенная версия

Полная версия - отчёт R1: `_bmad-output/planning-artifacts/research/competitive-seller-ai-assistants-foreign-analogs-bes-2026-09-02/research.md` (1676 строк, 313 источников, доступ 02.09.2026; 6 сегментов × 3 раунда + верификация; `claims` после проверки цитат 02.09: verified 70, disputed 29, overturned 7; проверка - `sections/_citation-check.md`). Что там есть и чего нет в PRD §16:

- **Матрица «области A-G × сегменты 1-6»** (раздел «Кросс-сегментный срез»): по каждой ячейке - продукты-носители со ссылками `[n]`, пометки «(сн.)» для поисковых сниппетов и «(unv.)» для неверифицированного. Области: A бриф и алерты, B аномалия → диагноз → действие, C память решений и сверка, D прогноз спроса и запасов, E guardrails рекламы, F отзывы и вопросы, G контент и листинг.
- **Сквозные пустоты матрицы:** область C пуста во всех шести сегментах; утренний дайджест с фиксированным временем и каналом (A) - пуст во всех шести; OOS-aware поведение рекламы (E) - только сегмент рекламных платформ; метод прогноза (D) раскрыт только в сегменте прогноза запасов и у Sellerboard.
- **Механика каждого паттерна** (как именно реализовано у носителей), которую §16 сжимает до одной строки: ступени по days-to-stockout с авто-восстановлением; статусы документа Draft → Sent for Approval → Approved; фильтр «Change By» в журнале изменений; блоки ежедневной выдачи (риск стокаута / PO требуют внимания / прогнозы к пересмотру / здоровье запаса).
- **Секции по сегментам** с разбором функций, цен (с датой доступа), позиционирования, траектории и голоса клиентов; **приложение источников** `[100]`-`[659]`; **карта устаревания** (104 датированных claim, 80 к перепроверке, расчёт `recon_kit.py staleness`).
- **Корректировки верификации**, важные при цитировании: рейтинг Helium 10 на Trustpilot - 2.1/5 по прямому измерению (вторичное «3-4 звезды» опровергнуто); режимы «suggest only / auto-approve» у Amazon Seller Assistant в первичном тексте отсутствуют (только «with permission») - вторичный источник оспорен; хронология «US rollout Dec 2025 / full autonomy Q2 2026» опровергнута; PPC bid automation у Sellerboard - оспорена.
