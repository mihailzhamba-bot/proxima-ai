### 0.2 Принципы развития продукта (Mike, 02.09.2026)

Нормативный текст для всего, что за пределами M-05 (§4.F, §12, §13, §16); в §0.1 - только история появления.

1. **Расчёты, а не копия.** Собственные наработки (скиллы, рутины) не переносятся как есть; из них извлекается расчётная логика и переформулируется как вычисляемые capabilities по каждому магазину на данных лестницы, детерминированным кодом, с источником у каждой цифры.
2. **ML - направление роста.** Прогнозы, аномалии и ранжирование считают модели по данным магазина; LLM объясняет, не считает (правило проекта). Каждая ML-цифра воспроизводима (модель, версия, входы, `run_id`) и проверяется сверкой ожидания с фактом.
3. **Best practices зарубежных аналогов** извлекаются глубоким ресёрчем и входят в PRD с источниками (§16), не из памяти.

## 1. Видение

Владелец кабинета WB каждое утро вручную смотрит кабинет, чтобы понять, упали ли продажи. Система должна показывать это сама: «вчера против нормы», по каждому магазину, с данными, которые собираются без участия человека, и цифрами, у каждой из которых есть источник. Дальше - аномалии с ценой в рублях, гипотезы причин с проверкой, запись решений и сверка «сработало ли». Ещё дальше - система решений и прогнозов по магазину, где расчёты и модели предлагают, а человек утверждает.

Три горизонта:

- **Горизонт 1 - сентябрь 2026, M-03.** Утром 30.09.2026 Mike открывает `/brief` и видит строку вида «29.09: N заказов против нормы M (−x %), выручка A ₽ против B ₽», статус «данные до 29.09, обновлено сегодня 06:xx»; цифры совпадают с кабинетом WB, и та же сводка приходила 7 утр подряд без ручного запуска (каноническая формулировка success signal сентября; SPEC Success signal; D6).
- **Горизонт 2 - октябрь 2026, M-04/M-05.** Аномалии в разрезе SKU и категории, отсортированные по потерянной выручке, шум отсечён (CAP-7); к каждой аномалии - гипотеза причины, что проверить, источник каждой цифры (CAP-8); решение записано, через заданный срок - сверка ожидания с фактом (Story 5.3).
- **Горизонт 3 - M-06+, предложение.** Система решений и прогнозов по магазину: спрос, сезонность, покрытие остатков, эффективность рекламы, события карточки - вычисляемые capabilities на данных лестницы с растущей долей ML и best practices зарубежных аналогов (§4.F, §12, §13, §16). Северная звезда из брифа - траектория доверия «рекомендует → одобряешь → автоисполнение по гейтам с kill switch». Она остаётся гипотезой за пределами лестницы (бриф, раздел «Видение»; §5).

## 3. Глоссарий

Канон терминов лестницы - `_bmad-output/specs/spec-wb-morning-brief/glossary.md`: термин с двумя значениями считается дефектом спецификации. Ниже канон процитирован дословно, затем термины PRD с привязкой к контрактам.

### 3.1 Канон (glossary.md, 30.08.2026)

- **Кабинет** - один продавец WB с собственным набором API-токенов; в БД = один `tenant`. Сентябрь: ИП Амирова О. Ф.
- **Заказы** - строки WB Statistics `orders` за календарный день по полю `date`, без `isCancel`. Метрика тревоги.
- **Продажи / выручка** - строки `sales` с `saleID` на `S`; выручка = сумма `finishedPrice`. Возвраты (`R`) в выручку не входят. Справочная метрика.
- **Полный день** - календарный день, за который сбор завершён после его окончания. Текущий день и день последней частичной выгрузки - неполные, в норму не входят.
- **Норма** - медиана заказов (и отдельно выручки) за 14 последних полных дней по кабинету целиком. Пересчитывается каждое утро.
- **Отклонение** - (вчера − норма) / норма в процентах, отдельно по заказам и выручке.
- **Аномалия** - отклонение, признанное сигналом (не шумом) и ранжированное по деньгам (M-04). Порог - открытый вопрос.
- **Сводка (brief)** - экран `/brief` веб-морды: статус данных, вчера против нормы, с M-04 - аномалии, с M-05 - план действий.
- **Ступень (M-xx)** - шаг лестницы M-00..M-05. Не фаза M1.
- **Единица работы** - один сеанс OpenHands + один связный PR + один результат, проверяемый Mike одним действием.
- **Прогон / run_id** - один запуск сбора или расчёта; каждая записанная строка несёт его `run_id`; прогон удаляется целиком.
- **Фикстура** - сохранённый реальный ответ WB API (без заголовков авторизации), на котором гоняются тесты. Канон - VPS `~/signal-inputs/fixtures/wb-api/` + S3.
- **Воронка** - дневные показатели по nmId из v3 sales-funnel / async CSV: открытия, корзина, заказы, выкупы. В сводке - октябрь.
- **Окно WB** - глубина, на которую Statistics отдаёт историю: ~6 месяцев скользящих (на 30.08.2026 - с 01.03.2026).
- **Боевая база / `proxima_test`** - одна база с данными кабинета и её копия для тест-запусков на том же Postgres. Сандбокс OpenHands - только `proxima_test`.
- **Ворота** - точки подтверждения заказчиком: 1 - инвентаризация, 2 - решения, 3 - единицы работы.

#### FR-26: Ежедневный сбор заказов и продаж

Система ежедневно забирает из WB Statistics заказы и продажи кабинета за прошедшие дни и накапливает дневной ряд кабинета (`fact_cabinet_daily`). Статус: `реализовано` частично (Story 1.3 реестр прогонов done), `сентябрь` (1.4, 1.6). Источники: CAP-1; epics FR1, FR2; AD-2, AD-3, AD-6.

**Consequences (testable):**
- Три дня подряд без ручного вмешательства в БД есть ряд за каждый день (CAP-1 success).

#### FR-38: Сигналы эффективности рекламы `[PROPOSED]`

Система ежедневно считает по каждой кампании и SKU признаки потери рекламного бюджета и выдаёт их как решения с ожидаемым эффектом; изменение кампаний система не выполняет никогда. Источник: CM-4; матрица отбора - третье место, runner-up. Предусловие: READ-токен категории «Продвижение» и allowlist по полному пути.

**Consequences (testable):**
- Набор сигналов: расход без заказов за N дней, доля рекламных расходов выше цели, конверсия ниже нормы кабинета, реклама на товар без остатка, проигрышные кластеры запросов, каннибализация SKU между кампаниями. Пороги - правила Policy Layer с источником и датой (FR-20), не константы в коде.
- Доля рекламных расходов считается двумя способами (по атрибуции и по обороту) с учётом возвратов; расхождение показывается, а не усредняется.
- Расход рекламы не суммируется дважды: сумма из статистики кампаний и удержание из финансового отчёта - один и тот же расход (правило из отчёта R2).
- Allowlist строится по полному пути и сверяется с признаком «только чтение» из спецификации; методы остановки и паузы кампаний вызываются через GET, поэтому запрещаются явно и по полному пути, а не по HTTP-методу (как в §12 CM-4).
- Каждый сигнал несёт оценку потерь в рублях с методикой расчёта и `source_refs`; «сэкономленный бюджет» без методики не публикуется.

#### FR-39: Поисковая видимость своих карточек `[PROPOSED]`

Система ежедневно собирает по своим ключевым запросам частоту, среднюю и медианную позицию, видимость, показы карточки, добавления в корзину и заказы, и сигнализирует о потере позиции. Источник: CM-12; матрица отбора - 58 баллов, шаг 5. Ступень: M-06+.

**Consequences (testable):**
- Работает на токене категории «Аналитика», который уже есть на сервере: нужна разведка и внесение в allowlist, а не новый токен.
- Обновление данных раз в час, история до 365 дней, лимит 3 запроса в минуту; выборка текстов запросов ограничена 30 позициями без подписки и 100 с подпиской - охват выбирается по приоритетным SKU из паспорта клиента (по спецификации R2, зеркало OpenAPI, уверенность средняя, живой проверки не было).
- Сигнал потери позиции считается против собственной нормы SKU, а не против конкурентов: сравнение с чужими карточками требует парсинга и остаётся non-goal (§5). Триггер сигнала - правило Policy Layer с источником и датой (FR-20), не константа в коде.

#### FR-40: Рейтинг и отзывы как события `[PROPOSED]`

Система фиксирует падение рейтинга товара и поток отзывов как события для диагноза; ответы покупателям система не публикует никогда. Источник: CM-11; матрица отбора - 56 баллов, шаг 5. Ступень: M-06+.

**Consequences (testable):**
- Событие «падение рейтинга к своей норме» считается на существующем токене «Аналитика» через отдельный метод рейтинга товара (обновление раз в час; по спецификации R2, живой проверки не было) - токен отзывов для этого не нужен.
- После получения токена «Вопросы и отзывы»: новый негативный отзыв по SKU и возраст неотвеченного отзыва как отдельные события. Порог возраста строго меньше 30 дней: после 30 дней без ответа отзыв уходит в архив платформы, и сигнал теряет смысл (по спецификации R2, живой проверки не было).
- Черновики ответов допустимы только с человеком в контуре; публикация ответа, отклонение вопроса и оформление возврата - операции записи в платформу, то есть non-goal навсегда (§5).
- Тексты покупателей - персональные данные: выбор провайдера языковой модели и места обработки подчиняется требованиям §11.1, а не удобству; решение - OQ-15.

- Torgstat и любая браузерная автоматизация в runtime.
- Восстановление списанных веток `pa-9`, `stash/pa-27-snapshot`; `now-orchestrator` вне лестницы.
- Любая запись в WB (цены, остатки, контент) - никогда.

Границы продукта, действующие на всех ступенях (v1 + v2):

- **WB WRITE - никогда**, включая действия, которые умеют собственные наработки: управление рекламными кампаниями и пополнение бюджета (`wb-promotion`, 14 write-команд), публикация ответов на отзывы и вопросы и оформление возвратов (`wb-reviews`, `wb-questions-autoresponder`), создание карточек (`wb-card-bootstrap`). Рекомендация человеку - можно; действие в WB - нет (extract-drops-C2, C3, C4).
- **LLM не считает метрики.** Цифры - детерминированный код или версионированная модель с SourceRef; LLM объясняет и формулирует текст (правило проекта; принцип 2).
- **Порт чат-скиллов «как есть»** (Excel/PDF-выход, LLM-арифметика, ручные пороги без источника) - не продукт; переносится расчётная логика (принцип 1).

- **Второй tenant** - после M-03, как строка в `tenants` + токены + инстанс таймера без изменения схемы (D18, AD-13); SaaS для селлеров (M3) - вне лестницы.

## 11. Ограничения и guardrails

Формулировки уровня capability; механизмы - в спайне (AD-n) и `addendum.md`.

### 11.1 Данные

- Источник - только официальный WB API кабинета, только READ-эндпоинты реестра AD-4; новый источник входит через разведку по образцу `API-FACTS.md` (живые вызовы - только Claude с сервера по явному разрешению, D5/D22), allowlist и гейт; write-эндпоинты гейт запрещает (AD-4). Мёртвые методы (§4.0) не используются.
- Любая цифра прослеживается до артефакта WB в CAS и `run_id` или до детерминированного расчёта (AD-1, SourceRef); цифры без источника не публикуются (SM-C4).
- Окно WB ~6 месяцев: история не копится сама; бэкфилл - до вытеснения (FR-27, NFR9).
- Одна модель данных на много кабинетов: `tenant_id` и RLS в каждой таблице; GUC `proxima.tenant_id` первым statement; второй tenant без изменения схемы (AD-13).
- Секреты не покидают VPS (`/etc/proxima-ai/secrets/`, `1010:1010 0600`, compose `secrets:`); значения никогда в env, логах, артефактах, фикстурах (AD-6, AD-13, epics NFR5). Обнаруженные в наработках копии токенов вне VPS (`~/.claude/wb-tokens/*.env`, `settings.json`, `credentials.py`) - в инвентарь и ротацию, в продукт не переносятся (extract-drops-C2, C4, C8).
- Персональные данные покупателей (`userName`, тексты и фото отзывов) и HR-данные из наработок в данные продукта не попадают без отдельного решения о хранении и сроках (extract-drops-C1, C3, C4); ретеншн - Deferred (AD-17); решение о ПДн и провайдере языковой модели - OQ-15.
- Тесты только на фикстурах; сеть в тестах запрещена; живой WB API - когда без него никак, ответ сразу в фикстуру (SPEC, AD-4). Обезличенные фикстуры в репозитории не больше 200 КБ, полные ответы - на сервере и в объектном хранилище; **в тестовом окружении токены не заданы вовсе** (epics NFR2).
- `[ASSUMPTION]` Референс тестов - `make verify` на маке (Homebrew PG16); зона OpenHands получает uv/node через `.openhands/setup.sh` (SPEC).

### 11.2 Архитектура

- Pipes-and-filters над неизменяемым реестром доказательств: evidence → observations → versioned facts → norm/signals → materialized brief; слои не пишут влево (спайн парадигма, AD-16).
- Обратимость: каждая строка несёт `run_id`, прогон удаляется целиком транзитивно; частичных данных не существует (AD-3, FR-29).
- Деньги - строка с двумя знаками в JSON, `numeric(14,2)` в БД; контракты - JSON Schema в `contracts/`, TS через codegen, Python через dataclass + jsonschema (AD-10, epics NFR13).
- Webapp только читает две view под read-only ролью и не ходит в WB; бизнес-логика вне Next.js (AD-9, AD-11, AD-16). Первая запись из UI (решения, ручные вводы) - новый AD до реализации (G-9, OQ-8). Исключение из AD-11, записанное спайном: в фазе 1 `funnel_csv` допускается owner-URI; других исключений нет.
- Переиспользование через ревью, не переписывание (SPEC constraint): незамерженный код ветвей `pmm-20-scn-001`, `pa41-full-w2-phase3`, `pmm29-contracts`, `ai/pa-50` входит только через ревью и provenance; переписывание с нуля - не вариант по умолчанию (`docs/state/MIGRATION-GAPS.md` §4).
- Расписание - хост-таймеры systemd с контейнерными one-shot шагами; «обновить сейчас» нет (AD-6).
- Без auth, ролей и публичного URL до октября; заморозки сентября: auth-зона webapp, `services/control-plane/src/proxima/`, business-signal pipeline и `raw-store.ts` (AD-18).
- Один VPS; боевая база + `proxima_test`; сандбокс OpenHands - только `proxima_test` (AD-12, D8).
- LLM не считает метрики: цифры диагноза - из сигнала и фактов; валидатор отклоняет число не из входа (FR-15).

### 11.3 ML-контур (принцип 2; OQ-11 - новый AD)

- Модель = версионированный код: имя, версия, параметры, обучающие входы (`run_id` фактов) фиксируются при каждом прогоне; выход модели несёт SourceRef на версию модели и входы и удаляется по `run_id` как любой прогон.
- Качество измеряется до показа: backtest на фикстурах и истории кабинета с метрикой ошибки (класс метрики - WAPE/MAPE по R2), затем сверка прогноза с фактом по паттерну Story 5.3; порог допуска - решение Mike (SM-8).
- Модель считает, LLM объясняет: текст диагноза не меняет числа модели; расхождение между выходом модели и нормой D21 - отдельный сигнал, а не замена нормы.
- Данные - топливо: 26 недель дневного ряда по кабинету и nmId (Statistics), воронка с даты первого серверного прогона (≈ 5 недель к 27.10, SM-7), остатки - после OQ-13; годовая сезонность из собственных данных недоступна до 03.2027 (окно WB), внешние priors - только опционально и с источником (extract-drops-C5).
- Границы среды: control-plane Python 3.14 на одном VPS; ресурсы и расписание обучения - в AD; провайдеры LLM - только через egress с VPS по одобрению Mike (PMM-31).
- **Лестница моделей (по итогам R2).** Сначала детерминированный baseline (медиана, покрытие в днях), затем методы интермиттентного спроса с конформными интервалами, затем глобальная модель с признаками-лагами. Каждая ступень допускается в сводку только после победы над предыдущей на rolling-origin backtest по метрике, зафиксированной до эксперимента. Обоснование: в исследованиях чисто ML-методы выигрывают на больших наборах, но типовые функции потерь градиентного бустинга не справляются с переизбытком нулей и разреженным спросом, а простые методы интермиттентного спроса на разреженных рядах дают ошибку порядка одной единицы товара в день (отчёт R2; для кабинета величина - `UNKNOWN` до backtest).
- **Дни отсутствия товара исключаются** из обучения и расчёта скорости, либо латентный спрос восстанавливается явно (инвариант; обоснование - FR-37 и отчёт R2, раздел о цензурированном спросе: двухэтапная схема на наборе FreshRetailNet-50K снижает систематическое занижение с 7.37 % практически до нуля).
- **Пороги аномалий - на устойчивых статистиках** (медиана и медианное абсолютное отклонение вместо среднего и сигмы), с отдельной проверкой на ложные срабатывания на рядах с недельным профилем (инвариант; детали - FR-36).
- **Минимально достаточная длина истории неизвестна**: свидетельств для дневных рядов SKU не найдено ни в одном источнике, вопрос решается собственным backtest, а не выбором из литературы.

## 15. Операционные требования

- **Утренний цикл**: `proxima-morning@<tenant>` в 05:30 Europe/Moscow, шаги `collect → funnel_v3 → norm → brief` (до утверждения CR к AD-6; после - `collect → norm → brief`, воронка отдельным юнитом); сводка за вчера доступна на `/brief` не позже 06:30 МСК (FR-22); семь утр SM-6 считаются по `collector_runs`, а не по факту доставки алерта; `OnFailure → proxima-alert@` в Telegram-канал монитора (AD-6, AD-17, epics AR3).
- **Dead-man для пользователя**: `stale` на `/brief` при отсутствии сбора > 24 ч или неполном вчерашнем дне (AD-7, AD-17).
- **Наблюдаемость**: одна JSON-строка на событие (`ts, level, run_id, tenant_id, kind, step, msg`) в journald; `collector_runs` - единственный источник статуса прогона (AD-17, epics NFR11).
- **Бэкап и восстановление**: ночной бэкап Postgres и `PROXIMA_RAW_DIR`; локальные дампы gzip, в S3 - через age; еженедельная проверка восстановления в `proxima_test` по понедельникам 06:00 до `funnel_csv` (AD-17, Story 1.12 done).
- **Поставка**: образы сервисов сбора и расчёта, одноразовые контейнеры из общего файла compose с секретами через механизм секретов, роли создаются идемпотентным скриптом provision после миграций (epics AR2, AR4).
- **Право блокировки релиза** (D26): релиз не выпускается, пока расхождение теневого пересчёта (`docs/state/SHADOW-RECONCILIATION.md`) или сверки с кабинетом (`docs/state/CABINET-RECONCILIATION.md`) выше допуска не закрыто одним из трёх способов - правится наш код, правится независимый пересчёт, либо Mike снимает блокировку записью в `DECISIONS.md` с причиной. До выяснения правильным считается число независимого пересчёта.
- **Релиз**: только по явному «деплой» от Mike, с записанным планом отката; релиз = тег + образы; откат = предыдущий тег + `delete_run` по прогонам релиза; миграции не откатываются (AD-15, D7); перед релизом - регрессия `WORKS-TODAY.md` целиком (epics NFR10).
- **Наблюдение после релиза**: сутки; для сводки - «пришла ли на следующее утро с верными цифрами»; не пришла - откат, не починка на боевом (epics AR16).
- **Ретеншн**: ничего не удаляется автоматически - Deferred (AD-17); решение вместе с ПДн (§11.1, OQ-15).
- **Токены**: analytics-токен ротируется на read-only до Story 3.1 (решение 7а, PA-13); все категории только READ.
- **Секреты**: файлы токенов именуются по схеме AD-13 (кабинет и категория); первый релиз M-01 включает переименование существующих файлов под эту схему (`mv`, спайн AD-13) как шаг runbook 1.13/1.14.
- **Доступ**: до октября - ssh-туннель `proxima-app`, `WEBAPP_REQUIRE_AUTH=false`; auth, Caddy и домен - октябрь (спайн Deferred, AD-18).
