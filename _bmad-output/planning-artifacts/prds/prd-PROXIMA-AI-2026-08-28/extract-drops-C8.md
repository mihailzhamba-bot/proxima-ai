## 1. `wb-agency-report` - брендированный клиентский отчёт end-to-end

### 1.1 Capability, пользователь, триггер, версия

- **Capability одной строкой:** по одному вызову CLI собрать данные кабинета WB (воронка по SKU + тарифы + реклама + рынок MPStats), прогнать через жёстко закодированный rule-engine (красные флаги / точки роста / рекомендации) и отрендерить тёмный брендированный A4-отчёт «Executive Analytics» (HTML → PDF) плюс `summary.md` для письма и `manifest.json` (SKILL.md:3-7, 17, 71-87).
- **Пользователь:** менеджер агентства запускает (`manager: "Mike"` SKILL.md:98); потребитель PDF - клиент/собственник кабинета (`--mode=client`); `--mode=manager` (операционный HTML-dashboard «по всем клиентам», SKILL.md:22, 131) заявлен, но шаблон `templates/manager/*.j2` в дропе отсутствует (render_html.py:132 ищет `{mode}/{template}.html.j2`; каталог `templates/manager/` не существует, есть только `templates/client/`).
- **Триггер:** фразы «отчёт для клиента», «презентация по продажам», «monthly review», «квартальный обзор», «manager dashboard», «данные по Ольге/другому клиенту + выводы» (SKILL.md:10-12, 21-25). Не использовать для сырых вызовов API, только рекламы, только отзывов, только тарифов (SKILL.md:27-32).
- **Версия:** SKILL.md:155 `0.1.0 (Phase 1 MVP)`; таблица фаз SKILL.md:126-133 помечает Phase 2-6 «запланирована», хотя в коде уже реализованы части Phase 3 (SVG-графики), 4 (MPStats, тарифы, реклама) и 5 (charts) - SKILL.md отстаёт от кода. Пустые каталоги `references/`, `examples/` (SKILL.md:151-153 на них ссылается).

### 1.3 Логика

**Конвейер (build.sh:96-353):** fetch WB → [fetch MPStats по топ-3 предметам клиента, derive через `transform.derive_top_subjects`, build.sh:118-150] → [fetch tariffs] → [fetch promo] → `transform.py` → `metrics.json` → `render_html.py` (Jinja2, autoescape, CSS по `branding.template`) → `html_to_pdf.py` (HeadlessChrome `--headless=new --print-to-pdf`, html_to_pdf.py:57-66) → `summary.md` + `manifest.json` (build.sh:262-349).

**KPI-сетка (8 карточек, transform.py:132-172):** Выручка = `orderSum` (заказанное, не выкупленное; :155), Заказы, Выкупы, Отмены (sub «Cancel% X vs Y», `alert` при cancel% > 0.18, :163), Показы, Корзина, Wishlist, Avg Check (sub «CTR · Buyout», где «CTR» на самом деле = cart/open, :152). Дельты - к прошлому периоду той же длины (`delta_str`, :66-72; «new», если прошлого нет).

**Rule-engine (transform.py:619-779) - все пороги захардкожены, источник порогов не указан:**

| Правило | Условие (цитата) | Текст/эффект | file:line |
|---|---|---|---|
| RED-1 «Показы упали - главный драйвер просадки» | `views_delta_pct < -0.20 and cart_delta_pct > -0.15` | гипотезы: потеря позиций в поиске, урезка РК, конкуренты, сезонность | transform.py:647-659 |
| RED-2 «Cancel% выше рынка (норма ~15%)» | `cancel_pct_sel > 0.18` | `potential_save = cancelSum * 0.25`; impact «Снижение cancel% до 15% = +…» | transform.py:662-672 (663, 665, 671) |
| RED-3 «Топ-1 SKU = N% выручки - риск моно-зависимости» | `top1_share > 0.10` | «Нужна стратегия диверсификации» | transform.py:675-684 |
| RED-4 «N SKU без заказов - мёртвый капитал» | `zero_share > 0.30` | impact «Возврат {stocks_balance × 0.5} через ликвидацию»; действия «вывести / скидка 50-70% / SEO» | transform.py:687-696 (692, 695) |

| Top-15 SKU | `cancel_high = cancel_pct > 20`; заметка о концентрации «Топ-N = X%, Топ-1 = Y%» | transform.py:588-616 (604, 611-614) |

**P&L (Phase 4-finale, transform.py:388-475), формула :392-396:** `revenue = sel_orderSum; commission = revenue × kgvpMarketplace(subject)/100; logistics = buyoutCount × avg(boxDeliveryBase по всем складам); margin = revenue − commission − logistics`. `DEFAULT_COMMISSION_PCT = 20.0` для неизвестного предмета (:406). Тарифные строки с русской запятой парсятся `_parse_tariff_value` (:335-350). В отчёте это названо «Реальная прибыль после удержаний WB» / «Маржа» (templates/client/executive-90d.html.j2:124, 146-148; TL;DR «Реальная маржа» transform.py:904), при этом не учтены себестоимость, платное хранение, возвраты, налоги (шаблон :125-126, 182-186; transform.py:952-953).

**Ad ROI (transform.py:480-585):** `spend = Σ days.sum`, `attributed_revenue = Σ days.sum_price` (модель атрибуции WB), `DRR = spend / выручка каталога × 100` (:559), `attr_drr = spend / attributed_revenue` (:562), `ROAS = attributed_revenue / spend` (:560), `attribution% = ad_orders / catalog_orders` (:561), CTR/CPC/CPM (:556-558). Ярлыки ROAS: `≥4 «отлично», ≥2 «норма», ≥1 «ниже нормы», иначе «убыток»` (transform.py:25-30). В шаблоне DRR-карточка `alert` при `drr_pct > 30`, подпись «norm <25%» (шаблон :213, 216); строка РК красная при `drr_pct > 30` (:267).

**Конкурентная картина (MPStats, transform.py:237-330):** позиция клиента среди брендов предмета (:264-268), доля рынка = revenue клиента / Σ revenue топ-100/200 брендов (:270-271; оговорка «не весь рынок» :942-943), топ-5 конкурентов без своих брендов и «Бренд не указан» (:273-294), бенчмарки топ-10 (средняя цена, рейтинг, выручка; :296-303), «Gap до top-10» (:306-307; в шаблоне как «×N» :331-333).

**TL;DR (transform.py:782-814):** headline «Выручка {period}: {rub} (↑/↓ ±%)», summary «Каталог N SKU, M брендов. Главная находка: {первый red flag}», буллеты = дельта выручки + до 3 флагов; при наличии источников добавляются доля рынка (:889-892), маржа (:903-907), реклама (:918-922).

**Методология внутри отчёта (transform.py:924-965; шаблон :475-523):** список источников с описанием эндпоинта + `caveats` на каждую расчётную ветку - хороший прототип «SourceRef на каждую цифру» (в терминах платформы - `source_refs`). Подписи «Источник: …» есть на каждой странице с данными (шаблон :114, 182-186, 274-277, 363-366). На последней странице формула-цель: `P&L = revenue − returns − commission − logistics − ad_spend − (cost × units)` (:509).

### 1.5 Переформулировка как capability PROXIMA

**Что становится вычисляемым (детерминированно, из фактов платформы):** весь `metrics.json` - это агрегат по периоду того, что платформа уже копит по дням на тенанта. В терминах PRD/задания: клиентский отчёт за неделю/месяц/квартал = свёртка `brief_daily`/`norm_daily` и сигналов за период (в текущих миграциях это `fact_order_counts`, `release_promoted_facts`, `stg_wb_nm_report_rows`, `dim_product`; контракты `signal`/`diagnosis`/`decision-record`/`client-passport` в `contracts/`). Конкретно:

| Блок отчёта | Источник в платформе | Статус |
|---|---|---|
| KPI-сетка, дельты к прошлому периоду, бренды, топ-SKU, концентрация | дневной ряд заказов/выкупов/отмен по nmId × агрегат за период (вместо одного вызова WB «за 90 дней» - сумма дневных фактов с `run_id`) | вычислимо на M-01/M-03 данных; «прошлый период» - из того же ряда, без доверия к `past` от WB |
| Red flags RED-1..4, growth | те же детекторы, что в утренней сводке (SCN-001 падение продаж = RED-1 в масштабе периода; OOS/мёртвый сток ↔ SCN-005), пороги из `client-passport` (`sales_drop_threshold_pct`, `days_cover_threshold_days`), калибровка PMM-35/OQ-4 | правила переносимы, пороги - в паспорт клиента, не в код |
| «Эффект / рекомендации» | Decision Memory + Verification (`decision-record.expected/actual/delta/outcome`) - отчёт показывает, что было решено и что дало | вместо выдуманных «+3-5%» - фактический outcome |
| P&L | тарифы WB (commission/box) + `cogs_status` из паспорта (решение Mike: COGS только по топ-SKU, memlog:18) | вычислимо; переименовать «маржа» → «выручка после удержаний WB» пока нет COGS |
| Ad ROI | WB Advert API - в платформе пока не собирается | новый источник данных (ДРР нужен и квартальному отчёту, §2) |
| Конкурентная картина | MPStats - решением Mike W2 / Non-Goal (memlog:12) | не в W1; сохранить как задел |
| Методология/caveats на каждой странице | `source_refs` из контрактов сигнала/диагноза | становится обязательным контрактом «каждая цифра с источником» |

**Что остаётся ручным / LLM-текстом:** объяснение «почему» (LLM-диагноз по PRD 4.6, с Reviewer), формулировка действий (сейчас генерятся шаблонами из правил - «Удвоить РК», «скидка 50-70%» - это прескриптив без источника, должен идти через Карточку решения и AM), тон/«вау» (LLM-редактура). Рендер PDF/HTML - детерминированный код.

**Ценность для цепочки Mike → операционный уровень → менеджеры:** сегодня это CLI на маке Mike под одного клиента (`--client=olga` во всех примерах и тестах), токены в домашних файлах, отчёт собирается руками раз в квартал. В платформе: отчёт по тенанту генерится по расписанию из тех же фактов, что и утренняя сводка (одна истина, одни `run_id`), менеджер получает manager-view (которого в дропе так и нет), клиент - брендированный PDF, Mike - ревью вместо сборки. Побочный эффект: раздел «что сделали → эффект» перестаёт быть «со слов менеджера».

**ML-потенциал: 1/3.** Отчёт = агрегаты и пороговые правила; единственное место для модели - baseline/сезонность для «ожидаемой» выручки периода (та же норма, что в SCN-001) и прогноз следующего периода. Всё остальное - арифметика; ML здесь скорее вредит объяснимости для клиента.

### 4.3 Логика

**Структура (:63-92):** `Участники` (клиент / Proxima) → `Повестка` → `Что решили` (решение - контекст + с чем согласились) → `Что я делаю` (чек-боксы, каждый со сроком `YYYY-MM-DD`) → `Что от клиента` (запрос - зачем, до какой даты) → `Следующий созвон` (дата/время, предварительная повестка) → `Insights / вопросы на подумать`.

**Правила (:94-108, 113-124):** action item = что + кто + когда, раздельно «я» vs «клиент» (:95-97); follow-up письмо/TG «Резюме: что решили, что я делаю, что от тебя», 5-10 строк, обязательно в 24 ч (:100-104, 120); memory update сразу, если новый факт (бренд, контакт, «новая ставка») или паттерн (:106-108, 121); «через пару дней» → дата (:117); «клиент сказал да» → на что именно (:119); «action items в общем» → кто + что + когда (:123). Сохранение `<Client>-debrief-YYYY-MM-DD.md` в `…/<Client>/debriefs/` (:110-111).

### 4.4 Выход

`.md` дебриф, action items, follow-up сообщение, update в project memory (:23-26, 99-108). Без брендинга. Потребители: Mike (память), клиент (follow-up).

### 4.5 Переформулировка как capability PROXIMA

- **Вычислимо:** ничего числового. Структурно: каждое «Что решили» = запись Decision Memory (`decision-record`: `decision`, `actor`, `decided_at`, `reason`, `expected`) с источником «созвон DD.MM», а «Что я делаю / что от клиента» с датами = задачи, к которым Verification позже привяжет `actual/outcome`. Так решения, принятые вне инбокса, попадают в тот же контур, что и решения по карточкам (PRD 4.7-4.8), и квартальный отчёт (§2) видит их автоматически.
- **Ручное/LLM:** извлечение структуры из transcript/notes - типовая LLM-задача (в среде есть Granola-транскрипты как коннектор), но результат - черновик на подтверждение Mike, не запись напрямую; follow-up текст - LLM по voice-профилю.
- **Ценность для цепочки:** для Mike - «что обещали клиенту» перестаёт жить в голове; для операционного уровня - сроки обязательств видны рядом с сигналами; для менеджеров - единый формат передачи клиента. В W1 не нужен (один пользователь), но задаёт контракт «решение вне системы» для Decision Memory.
- **ML-потенциал: 0/3.**

### 4.6 Код к переиспользованию, секреты

Кода нет. Переиспользовать структуру :63-92 как форму «внешнее решение» в Decision Memory и правило «кто + что + когда» как валидацию. Секретов нет.

### 4.7 Красные флаги

- Персональные данные: имена участников созвонов, «собственница Кристина» (:44), контакты и «новая ставка» (:106) в memory-файлах - при переносе в платформу это персональные и коммерческие данные тенанта, нужен контроль доступа.
- Transcript созвонов как вход (:20, 51) - согласие на запись/обработку не упомянуто.
- Обязательства «что от клиента до даты» - без механизма верификации остаются обещаниями в тексте.
- Внешние зависимости (voice, memory-файлы, Obsidian-пути) вне дропа.
