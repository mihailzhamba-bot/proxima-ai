### 3.3 Логика
**Подбор 3 конкурентов «диагональю»** (`data-sources.md:76-89`): фильтр `brand != наш`, `reviewRating ≥ 4.5`, `feedbacks ≥ 20`, цена ±40 %, vision-проверка релевантности первых ~15; слоты: ТОП-1 выдачи, лидер по отзывам (max `feedbacks` в топ-30), «двойник» (vision-схожесть + цена); при <3 — коридор ±60 %, отзывов ≥10 (`:89`, `SKILL.md:100`). ### 4.3 Логика: что считает код, что LLM
**Код — `scripts/process_semantics.py` (этап 4):**
- Стоп-слова `STOP` (`:34`), «сверхобщие» `GENERIC = {косметик, уход, товар, средств, корея, корейск, женск, мужск}` (`:36`) — **захардкожен под тест на косметике**, вопреки заявленной обобщаемости (`:11`); суффиксный стеммер `ENDINGS` (`:37-49`), `normkey` = отсортированные основы слов = id кластера (`:57-58`).
- «Корни товара» = основы из `subjectName + title + топ-30 запросов WB по частотности`, длина ≥4, не GENERIC (`:81-89`).
- Запросы WB без фильтра (`:92-98`); запрос MPStats остаётся, только если делит ≥1 корень (`:100-109`); при совпадении — `frequency = max` и оба источника (`:110-116`).
- Частотность кластера = сумма; перцентили `p20`/`p70` по кластерам → ВЧ/СЧ/НЧ (`:123-133`); кап 250 строк: все WB + топ MPStats (`:135-140`); `mode` full / new_card / degraded (`:142-146`); флаг `priority` по `normkey` или подстроке (`:121-122`).
- Расхождения доки и кода: `norm_query` MPStats фактически не используется как id кластера (док `semantics-and-description.md:30`, код `:120`); `pymorphy3` в коде отсутствует.

**Код — `build_semantics_xlsx.py`:** листы «Семантика» (кластер, запрос, показы, заказы, источник, тип, приоритетный, в варианте A/B — по вхождению нормализованной подстроки `q in var_a`, `:89`), «ТОП-5 конкурентов», «Методология» (`:66-161`).

**LLM (этапы 5-6):** генерация 2 вариантов (A — по сценариям, B — по выгодам; `semantics-and-description.md:87-92`), порядок расстановки ВЧ → лид, СЧ → тело, НЧ → детали (`:94-100`); **правило плотности** «вторичный кластер ≤4 вхождений, головной 7-8 на 3000-5000 знаков», порог WB неизвестен — «открытый вопрос для специалиста Р+» (`:57-65`); чек-лист 8 пунктов (длина ≤5000, плотность, приоритетные, стоп-слова, запрещённое, чистый текст, ≥90 % ключей из списка, читаемость; `:108-117`) — исполняется LLM, кодом не проверяется; рекомендации по незаполненным характеристикам «у 4 из 5 конкурентов заполнено» (`:123-129`).

### 4.5 Переформулировка
- **Единственный в кластере источник, дающий ежедневный per-tenant признак на имеющемся скоупе:** `search-texts` по своим nmId → таблица `query × nmId × день`: `frequency`, `orders`, `openCard`, `addToCart`, `avgPosition`, `visibility`. Из неё детерминированно: падение/рост `avgPosition` по топ-N запросам, потеря `visibility`, конверсия `orders/openCard` по запросу, доля «заказных» запросов — это и есть «позиция в поиске» из §1 (#13) и материал для SCN-011 (контент/поиск; скоуп потерян в PA-45). Условия: проба с сервера (2-3 вызова), запись в allowlist `tools/verify_business_signal.py`, выяснить лимит глубины периода и зависимость от «Джем»; лимит 3/мин при 20 nmId/вызов — ок для одного кабинета.
- Обработка семантики (кластеризация/перцентили) — переносится как модуль нормализации запросов; `GENERIC` заменить на конфиг per-tenant или убрать.
- Не переносимо: MPStats-запросы предмета, описания конкурентов с CDN, генерация текста как продукт (не аналитика; WRITE в карточку всё равно запрещён — сгенерированный текст некому применить в лестнице).
- **ML-потенциал: 2.** Детерминированно — ранжирование запросов по `orders/openCard` и детекция сдвига позиций; далее — кластеризация запросов эмбеддингами вместо стеммера, прогноз «какой запрос теряет позицию раньше падения заказов» (нужно ≥8 недель истории). LLM — только объяснение (по принципу «ML считает / LLM объясняет», memlog 2026-09-02).

### 4.6 Код к переиспользованию
7 Python-скриптов + `run_pipeline.sh`, только stdlib (`urllib`, `json`) и `openpyxl`; все проходят `py_compile`. Тестов нет. ### Выводы
1. Ни один скилл кластера не пишет в WB — как продуктовые действия все они READ + ручное применение продавцом; правило «WRITE запрещён» не нарушается, но и «применить результат» в лестнице некому.
2. Все пять зависят от источников, запрещённых или недоступных в проекте: платный MPStats (4 из 5), скрейпинг карточек/выдачи конкурентов (все 5: Firecrawl, CDN `card.json`, `search.wb.ru`, `feedbacks*.wb.ru`), скоупы «Контент» и «Отзывы» (токенов на сервере нет). Колонка «конкуренты» из аудита карточки не воспроизводима на лестнице в принципе.
3. Единственный вычислимый ежедневный per-tenant сигнал, который кластер реально приносит, — поисковая видимость своих nmId через `POST /api/v2/search-report/product/search-texts` (`frequency, orders, openCard, addToCart, avgPosition, visibility` по запросу): скоуп есть, эндпоинт нужно пробовать, включать в allowlist и проверять зависимость от «Джем». Это кандидат на SCN-011 (скоуп потерян в PA-45) и закрывает параметр «позиция в поиске» из аудита.
4. Второй дешёвый сигнал — детекция изменения контента своей карточки (hash описания/характеристик/фото) + линтеры (≤60/≤2000, скобки, ссылки, бренд в названии): требует единицы «токен Контент READ-only + allowlist», код тривиален.
5. Конверсии «корзина → заказ» и «% выкупа» из аудита уже доступны из `v3/sales-funnel/products/history` (7 дней) — сравнивать со своей нормой, а не с медианой топ-5; CTR и позиции без новых источников не считаются.
6. Скор «прожарки» существует в двух несовместимых версиях (roast: 18 параметров, веса 1/2, медиана, 30 дней; routine: другие 18, Σ117, топ-1, 90 дней) — как формула для PRD не готов; брать только механику подсветки/исключения «нет данных».
7. Единственный настоящий код — этап 4 `wb-seo-description` (нормализация, фильтр по корням, перцентили ВЧ/СЧ/НЧ) и валидаторы `wb-card-bootstrap`; тестов нет нигде, `GENERIC` захардкожен под косметику, валидаторы контента проверяют ответ LLM, а не факты.
