### 1.3 Расчёт (дословно, `ABC/scripts/compute_abc_forecast.py`)

Параметры: `LEAD_TIME_DAYS = int(env, 14)` (`:29`); `DAYS_OBS = (OBS_END − OBS_START).days + 1` (`:32`), по умолчанию 30 (`run_pipeline.sh:16-21`). Окна прогноза: `fc_start = OBS_END + 1`, `f30_end = fc_start + 29`, `f60_end = +59`, `f90_end = +89` (`:82-85`).

1. **Чистый спрос и среднедневные продажи** (`:120-123`):
   `clean = max(0, orderCount − cancelCount)`; `raw_avg = clean / DAYS_OBS`.
   Обоснование: отмены ≈ 4–5 % завышают спрос; выкупы (`buyoutCount`) — лагающий сигнал 3–7 дней, не используются (`methodology.md:26-28`). WB-поле `avgOrdersCountPerDay` игнорируется.
2. **Сезонный коэффициент, взвешенный по дням** — `weighted_factor(season, d_start, d_end, "season_sales")` (`:54-72`):
   считает `days_per_month` внутри окна; `weighted_pct = Σ_m season_sales[m] × days_m / total_days`; `factor = 1 + weighted_pct / 100`; нет данных по предмету → `factor = 1.0` (`:61-62`); отсутствующий месяц → 0 % (`:70`). Пример из документации: период 09.04–08.05 → `(22/30)·f_апр + (8/30)·f_май` (`ABC/SKILL.md:85`; `methodology.md:43-49`).
   Факторы считаются **на предмет** (`subjectId`), все SKU предмета получают одинаковые `f_obs, f_30, f_60, f_90` (`:89-107, 114-118`).
3. **Нормализация к среднегодовому** (`:125`): `norm_avg = raw_avg / f_obs` (если `f_obs == 0` → `raw_avg`).
4. **Прогноз на 30/60/90** (`:127-129`): `forecast_N = norm_avg × N × f_N`.
5. **Целевой запас с lead time** (`:131-134`): `avg_during_lead = norm_avg × f_30`; `target_N = forecast_N + avg_during_lead × LEAD_TIME_DAYS`. Буфер на lead time для всех трёх горизонтов считается по `f_30`.
6. **Дозаказ («сколько везти»)** (`:136-142`): `total_stock = stocks.wb + stocks.mp`; `deficit_N = max(0, round(target_N − total_stock))`.
7. **Покрытие остатков в днях** (`:144`): `cover_days = total_stock / avg_during_lead`, если `avg_during_lead > 0`; иначе `None` при `total_stock > 0`, иначе `0`.
8. **ABC по выручке** (`:183-198`): сортировка по `orderSum_30d` убыв., кумулятивная доля `cs`; `cs ≤ 80 → A`, `cs ≤ 95 → B`, иначе `C`. Граница включающая (`ABC/SKILL.md:177-180`). ABC по штукам отвергнут осознанно (`ABC/SKILL.md:130`; `methodology.md:109`).
9. **Светофор OOS-риска** (`:200-213`): `raw_avg_per_day == 0 → «нет продаж»`; `cover is None → «в избытке»`; `cover < LT → «критично»`; `cover < LT+14 → «высокий»`; `cover < LT+30 → «средний»`; иначе `«в порядке»`. Обоснование порогов — `methodology.md:121-128` (без внешнего источника, инженерная эвристика).
10. **«Упали в ноль»** (лист OOS, `ABC/scripts/build_xlsx.py:383-397`): `selected.orderCount == 0 and past.orderCount > 0`. **Баг:** `pastPeriod` в запрос не передаётся (`fetch_wb_data.py:58-63`), хотя `api_endpoints.md:23` его требует для этого блока → `s["past"]` либо отсутствует (KeyError, падает вся сборка), либо блок всегда пуст.

Дублирование в Excel-формулах (`build_xlsx.py:259-283`; `xlsx_layout.md:68-103`): `I = IFERROR(G/H,0)`; `M/N/O = ROUND(I*{30|60|90}*{J|K|L},0)`; `P/Q/R = ROUND({M|N|O} + I*J*'Сводка'!$B$4, 0)`; `U = S+T`; `V = IFERROR(U/(I*J),"-")`; `W/X/Y = MAX(0, {P|Q|R} − U)`; `Z = IF(G=0,"нет продаж", IF(V<B4,"критично", IF(V<B4+14,"высокий", IF(V<B4+30,"средний","в порядке"))))`. Lead time — единственная редактируемая ячейка `'Сводка'!B4` (`build_xlsx.py:80-88`). Несогласованность: на листе ABC подсветка покрытия жёстко `< 14` (`build_xlsx.py:203-207`), не привязана к B4; в Excel нет состояния «в избытке» (при `V = "-"` формула даёт «в порядке»).

**Что НЕ считается (объявлено явно):** страховой запас по волатильности `Z × σ × √(N + L)` — «нужны дневные данные ≥ 90 дней, funnel-history даёт 7 дней» (`ABC/SKILL.md:206`; `methodology.md:80,132-138`); эвристика «+20 % A / +10 % B / 0 % C» описана, не реализована (`methodology.md:140`); тренд SKU `selected/past` (`ABC/SKILL.md:207`; `methodology.md:142-144`; `xlsx_layout.md:168`); промо/акции (`ABC/SKILL.md:210`); категорийная сезонность вместо предметной (`ABC/SKILL.md:208`); **OOS-дни** — коррекции среднего на дни с нулевым остатком нет вообще (только агрегат за 30 дней без дневного ряда; «нет продаж — проверь, не OOS ли это» вручную, `ABC/SKILL.md:121`); точка заказа как отдельная величина не выводится — де-факто ею служит порог `cover < lead_time` («критично»), а `target_N` играет роль order-up-to level.

**Код vs LLM:** все числа — детерминированный Python + формулы Excel. LLM: собирает ключи и lead time (`ABC/SKILL.md:26-34`), запускает шаги, сверяет контрольные суммы и **«пересчитай вручную forecast и target по топовому товару»** (`ABC/SKILL.md:192-203`) — это LLM-арифметика в роли проверки (в PROXIMA недопустимо как источник, допустимо только как тест на фикстуре). Интерпретация отчёта продавцу не скриптована.

### 1.6 Красные флаги

1. **MPStats — обязательная платная зависимость** даже для ABC и покрытия (`run_pipeline.sh:9`); сезонность целиком из «смоделированной» кривой третьей стороны, дата кривой в отчёт не попадает (только название источника, `build_xlsx.py:326,495`).
2. **Оба WB-эндпоинта вне реестра AD-4 и не проверены** (`API-FACTS:34`; `stocks-report/offices` не упоминается); один из них ещё и не используется.
3. Нет страхового запаса и обработки OOS-дней: среднее за 30 дней занижено для SKU, стоявших часть периода в нуле → дозаказ занижен именно у проблемных товаров.
4. Буфер lead time по `f_30` для 60/90; пороги светофора (`+14`, `+30`) и ABC (80/95) — эвристики без источника (Парето упомянут `methodology.md:107`, Silver & Peterson — `:156`, без конкретики).
5. LLM просят «пересчитать вручную» — противоречит правилу «LLM не считает метрики».
6. WRITE в WB: **нет**. Torgstat/браузер: нет.

## 2. `wb-seasonality-forecast`

### 2.1 Capability, пользователь, триггер, версия

- **Capability:** по артикулу/URL/категории WB определить предмет, взять годовую кривую сезонности предмета из MPStats, посчитать индекс 0–100 по месяцам, пик/провал/амплитуду, уровень доверия, окно отгрузки на склад WB (пик − 4–6 нед.) и окно закупки у поставщика (− `supplier_lead_weeks`); Excel 3 листа + PDF (`SEAS/SKILL.md:3,8`).
- **Пользователь:** продавец WB, «новичок в Claude/Cowork» — скилл включает гайд первого запуска и 2-шаговый онбординг (`SEAS/SKILL.md:45-114`; `references/first-run-guide.md`, `onboarding.md`).
- **Триггер:** только явные вопросы о сезонности: «когда сезон у …», «в каком месяце пик», «когда закупать/отгружать к сезону» (`SEAS/SKILL.md:16-24`); не активируется для «сколько» — это `wb-abc-seasonal-forecast` (`:26-31`).
- **Дата версии:** 28.05.2026 (`MANIFEST.md`); живой прогон 25.05.2026 на артикуле 39526310 / предмет 5312 (`SEAS/SKILL.md:190`; `seasonality_report.py:13`; `api_endpoints.md:5`).

### 2.3 Расчёт (дословно, `SEAS/scripts/seasonality_report.py`)

1. **Множитель месяца** (`:156-166`): `by_month[m] = season_sales` из записи с `date "MM-01"`; `factor_m = 1 + season_sales_m / 100`; отсутствующий месяц → `None`.
2. **Индекс 0–100** (`:170-172`): `index_m = round(factor_m / max(factor) × 100, 1)`; у пика 100.
3. **Пик / провал** (`:173-174`): месяц с max / min `factor`.
4. **Амплитуда** (`:175`): `amp = max(factor) / min(factor)` (0, если min = 0).
5. **Уровень доверия** (`:177-180`; таблица `SEAS/SKILL.md:213-218`): `n == 12 and amp > 1.5 → «Высокий»`; `amp < 1.2 or n < 6 → «Низкий»`; иначе `«Средний»` (`n` — число месяцев с данными). Пороги 1,2× / 1,5× — «по правилам ТЗ» (`SEAS/SKILL.md:211`), внешнего источника нет. Скилл сам признаёт: эндпоинт почти всегда отдаёт 12 месяцев, признак «новая ниша < 6 мес.» по нему не определяется — открытый вопрос специалисту (`SEAS/SKILL.md:221`; `api_endpoints.md:149-150`).
6. **Окна закупки/отгрузки** — `windows(peak_month, supplier_lead_weeks, today)` (`:184-197`):
   `yr = today.year if date(today.year, peak_month, 1) > today else today.year + 1`; `peak_start = date(yr, peak_month, 1)`;
   `ship = [peak_start − 6 нед., peak_start − 4 нед.]`; `buy = ship − supplier_lead_weeks`; `on_time = today ≤ buy_b` (поздняя граница) → «успеваете к пику» / «к ближайшему пику не успеваете — следующий цикл».
   «4–6 недель до пика» помечено как допущение, требующее подтверждения специалистом (`SEAS/SKILL.md:230`; `:404-406`); «пик» = первое число месяца-пика.
7. **Когда рекомендация не выдаётся** (`:400-402`): только при `«Низкий» и months_present < 6` — «Низкий» из-за амплитуды < 1,2× всё равно получает окна (`SEAS/SKILL.md:292` обещает окна только для Высокий/Средний — расхождение документации и кода).

Не считается (границы, `SEAS/SKILL.md:38-41`): объёмы в штуках, собственные продажи продавца, конкуренты, промо, тренд, OOS, страховой запас. Ozon — задел в архитектуре (`api_endpoints.md:178-186`), не реализован.

**Код vs LLM:** явное разделение (`SEAS/SKILL.md:167-171`): скрипт — резолв, API, расчёт, отчёт; Claude — онбординг, разбор запроса, интерпретация JSON-сводки. Единственная «мягкая» зона — эвристика «новая ниша» отдана LLM/специалисту (`SEAS/SKILL.md:221`).

### 3.3 Ежедневный расчёт «покрытие остатков в днях» (per tenant × nmId, шаг `norm` после `collect`)

```
rate_alert(nm, D)  = median(orders_clean(nm, d), d ∈ последние 14 полных дней)          -- D21-совместимо, для тревог
rate_plan(nm, D)   = mean(orders_clean(nm, d), d ∈ последние 28 полных дней, stock_wb(nm, d) > 0)  -- для закупки; OOS-дни исключены
                     если дневных остатков ещё нет: OOS-день ≈ (orders_clean(nm,d) = 0 ∧ rate_alert > 0 ∧ stock_wb(nm,D) = 0) → пометка UNKNOWN
stock_total(nm, D) = stock_wb(nm, D) + stock_fbs(nm, D)            -- stock_fbs из ручного ввода, иначе 0 с пометкой
cover_days(nm, D)  = stock_total / rate_plan                        -- NULL при rate_plan = 0 («нет продаж»/«в избытке» — два разных статуса, как в скилле)
oos_date(nm, D)    = D + cover_days
status             = критично, если cover < lead_time_days; высокий < lead+14; средний < lead+30; иначе норма   -- пороги скилла, калибровать (PMM-35)
OOS Alert          = oos_date < дата ближайшей подтверждённой поставки из stg_supply_plan  (FR-11)
Procurement Alert  = cover_days < lead_time_days + safety_days ∧ нет поставки, закрывающей разрыв   (точка заказа, prd.md:95)
safety_days        = Z × σ(orders_clean, 28–56 дн.) × √(lead_time_days) / rate_plan   -- Z = 1.645 (95 %) как параметр Policy Layer; то, чего скилл «не мог» из-за 7 дней истории, а у PROXIMA 26 недель
deficit_N(nm, D)   = max(0, rate_plan × (N + lead_time_days) × wd_factor_N − stock_total),  N ∈ {30, 60, 90}
ABC(nm, D)         = по Σ revenue за 30 дней, пороги 80/95 включающие
```

Каждая строка результата: `tenant_id, nm_id, calendar_day, run_id, model_version, входы (stock_as_of, окно, lead_time_days)` — по правилу «каждое число с источником и датой». Отличие от скилла: две скорости (медиана для тревоги, среднее без OOS-дней для объёма), страховой запас из собственной волатильности, поставки из `stg_supply_plan` вместо одного `lead_time` из env.

### 3.4 «Прогноз спроса по SKU» и сверка с фактом

```
forecast(nm, made_on = D, h ∈ {30, 60, 90}):
  B0 «медиана14 × h»            -- baseline, D21-совместимый
  B1 «сезонный наив по дню недели»: Σ_{d=D+1..D+h} rate_plan × wd_factor(weekday(d))   -- wd_factor из 26 недель own-data
  B2 Croston / SBA / TSB           -- для интермиттентного спроса (класс C, много нулей)
  M1 глобальная модель (LightGBM/квантильная) по всем nmId арендатора — не раньше 4–6 месяцев накопления fact_stock_daily + fact_funnel_daily
хранить: forecast_daily(tenant, nm_id, made_on, horizon, p50, p90, model_version, run_id)
сверка через h дней (шаг Verification, prd.md:92): actual = Σ orders_clean(nm, D+1..D+h)
  per nm: APE = |F − A| / A (только A > 0); портфель: WAPE = Σ|F − A| / ΣA, bias = Σ(F − A) / ΣA; MASE против B0
  отчёт раз в месяц по классам A/B/C и по горизонтам; модель побеждает baseline только при WAPE ниже на согласованный порог два месяца подряд
```

Исход сверки — в терминах PRD: подтвердилось / не подтвердилось / частично / UNKNOWN (нет остатка → спрос цензурирован, сверка невозможна).

### 3.5 ML-потенциал (детально)

- **Класс задачи:** прогноз временных рядов по SKU с **интермиттентным** (zero-inflated) спросом и **цензурированием** (нулевые продажи при нулевом остатке ≠ нулевой спрос); плюс иерархия SKU → предмет → кабинет (reconciliation).
- **Данные сейчас:** 26 недель дневных заказов по nmId (≈180 точек на SKU) с ценой; воронка по nmId с 01.09.2026; **нет** истории остатков (→ цензурирование не снимается), нет промо-календаря, нет ≥ 12 месяцев для годовой сезонности.
- **Горизонты:** 30/60/90 дней; для 60/90 без годовой сезонности ошибка неизбежно растёт — честно показывать P50/P90 и «UNKNOWN: сезонность».
- **Метрики:** MAPE непригоден (нули в знаменателе), использовать WAPE, MASE/RMSSE, bias; для страхового запаса — квантильная ошибка (pinball) на P90; метрика продукта — доля SKU, ушедших в OOS вопреки прогнозу «в порядке».
- **Baseline vs ML:** B0/B1/B2 покрывают 80 % ценности (покрытие, дозаказ, светофор) и обязаны быть первыми; ML (M1) оправдан после накопления остатков и воронки и только если бьёт B1 по WAPE на классах A/B. MPStats-кривая — не ML, а внешний prior (W2).
- **Оценка: 2 из 3.** Данных достаточно для детерминированных baseline и интермиттентных методов уже сейчас; полноценный ML (3) блокируют отсутствие истории остатков и годовой сезонности. Для скилла №2 («когда пик») ML не нужен вовсе — нужна кривая ≥ 12 месяцев: own-data с марта 2027 либо внешняя.

**Выводы**

1. Оба скилла честные и read-only, вся арифметика в коде; но **весь домен сезонности стоит на платном MPStats**, а ABC/покрытие/дозаказ у скилла №1 без MPStats даже не запускаются — в PROXIMA сезонность надо отделить от запасов и сделать опциональным prior (W2), запасы — считать сразу.
2. **Ни один WB-эндпоинт скиллов не входит в реестр AD-4 и не проверен** (`v3/sales-funnel/products`, `v2/stocks-report/offices`); проверенный `products/history` не отдаёт остатки. Первый технический шаг кластера — 2–3 проверочных вызова остатков с сервера по политике allowlist.
3. **Остатки по SKU — единственный блокер** покрытия и OOS-дней: `supplier/stocks` мёртв, `wb-warehouses` не проверен и хранит остаток одного nmId. Без ежедневного `fact_stock_daily` нет ни SCN-005 по SKU, ни честной сверки прогноза (спрос цензурирован).
4. У PROXIMA есть то, чего у скилла №1 не было: 26 недель дневного ряда по nmId → страховой запас `Z × σ × √L` и исключение OOS-дней считаются из собственных данных; нужно принять два определения скорости (медиана 14 — тревога, среднее 28 без OOS — объём).
5. Годовая сезонность по предмету из own-data невозможна до марта 2027 (скользящее окно 6 месяцев) — «когда пик» в W1 Non-Goal; накопление истории с сентября обязательно, иначе и в 2027 базы не будет.
6. ML-потенциал кластера 2/3: сначала baseline (медиана × h, день недели, Croston для хвоста), метрики WAPE/MASE/bias и ежемесячная сверка; глобальная модель — после накопления остатков и воронки.
7. Переиспользовать стоит только спецификации формул (§1.3, §2.3) и лестницу статусов; код (openpyxl, urllib-клиенты, кэш в `tmp/`, LibreOffice recalc) в архитектуру AD-2…AD-6 не встраивается; тестов и фикстур в дропе нет.
8. Найденные дефекты дропа: `pastPeriod` не запрашивается (лист OOS сломан), мёртвый вызов stocks-offices, категорийный fallback с неверным `path`, игнорируемый `shipment_buffer_weeks`, токен MPStats открытым текстом в рабочей папке — при переносе логики ничего из этого не наследовать.
