### 1.4 Что это означает для PROXIMA [оценка]

**A1. Unit-экономика по артикулу со сверкой с недельным финотчётом.**
- Переформулировка per-tenant на данных лестницы: для каждого `nm_id` за закрытую неделю финотчёта — выручка `retail_amount`, к перечислению `ppvz_for_pay`, комиссия `ppvz_sales_commission`, логистика `delivery_rub`, хранение `storage_fee`, штрафы `penalty`, удержания `deduction`, приёмка `acceptance` (поля `reportDetailByPeriod`, `API-FACTS.md:28`, 96 полей) минус себестоимость × количество минус налог по ставке месяца = чистая прибыль; маржа = прибыль / выручка. Формула — собственная детерминированная с SourceRef на строки отчёта; вендорская формула PENDING, паритет проверить нельзя.
- Данные у PROXIMA: `reportDetailByPeriod` — **есть, но под гейтом**: 31 месяц, недельный разрез, лаг закрытия 1-8 дней (`API-FACTS.md:9`); в signal runtime запрещён `tools/verify_business_signal.py:27-29`; finance-api `sales-reports/detailed` реализован в `wb-client.ts:192-243`, живым вызовом не проверен (`API-FACTS.md:34, :54`). «Эквайринг» как отдельное поле в 96 не проверял — UNKNOWN. Себестоимость и помесячный налог — **нет**, нужна per-tenant таблица ручного ввода (см. A5).
- Что означает «сверка» у PROXIMA: финотчёт и есть источник денег; второго оценщика (по ставкам тарифов) в лестнице нет, сверять пока нечего. Различие продуктовых форм: у вендора одна гранулярность — неделя (интерпретация автора: задана источником); у PROXIMA дневной ряд «вчера против нормы» из orders/sales плюс недельная денежная сверка из финотчёта — две гранулярности с явным лагом второй.
- WRITE / парсинг: нет, контур A. Зависимость от PENDING: **средняя** — capability определима на своих данных, паритет по формулам и глубине истории оценить нельзя.

**A2. Реклама и ДРР «без задвоений».**
- Данные у PROXIMA: **нужен новый READ-источник** — advert-api, категория токена «Продвижение»; токена на сервере нет (`INVENTORY.md:215`), ни один advert-эндпоинт в реестре не проверен. Присутствуют ли рекламные удержания в финотчёте (`deduction` / `supplier_oper_name`) — не проверял, UNKNOWN.
- Механика дедупликации вендора PENDING → **нельзя оценить** паритет. Собственное правило (оценка): один источник истины по деньгам — финотчёт, статистика кампаний только для разреза по кампаниям; это снимает «задвоение» по построению, но требует проверки, что финотчёт содержит рекламу.
- WRITE: нет (статистика кампаний READ; в advert-api есть GET-мутации, их в allowlist не брать). Зависимость от PENDING: **высокая**.

**A3. Остатки FBO/FBS, динамика склада, остатки по регионам.**
- Данные у PROXIMA: `supplier/stocks` мёртв (`API-FACTS.md:10`); замена `analytics/v1/stocks-report/wb-warehouses` есть в коллекторе, живой вызов не делался (`API-FACTS.md:34`) → **нужен новый READ-источник (не проверен)**, токен категории «Аналитика» на сервере есть. «Динамика склада» = ежедневный снимок остатков с `run_id` в свою таблицу — снимков сегодня нет, так как нет источника.

| Жёсткая привязка к МСК — решение, а не ограничение | вендор объясняет прямо: так датирует заказы сам WB; перевод в пояс покупателя разошёлся бы с первоисточником, в пояс продавца — сместил бы пики |
| «Логистические разрезы» не раскрыты нигде | формулировка встречается один раз без пояснения; склад отгрузки, тип доставки или маршрут — «различить по публичным данным нельзя» |

### 2.4 Что это означает для PROXIMA [оценка]

**B1. Тепловая карта день × час с разрезами регион / артикул / размер / категория / цена / склад.**
- Данные у PROXIMA: **есть** — строка `supplier/orders` несёт 27 полей: `date`, `lastChangeDate`, `nmId`, `supplierArticle`, `techSize`, `subject`, `category`, `brand`, `regionName`, `oblastOkrugName`, `countryName`, `warehouseName`, `warehouseType`, `priceWithDisc`, `finishedPrice`, `totalPrice`, `discountPercent`, `spp`, `isCancel`, `cancelDate`, `srid`, `gNumber`, `sticker`, `incomeID`, `isSupply`, `isRealization`, `barcode` (фикстура, см. §0; `API-FACTS.md:25`). Тепловая карта = группировка по `weekday(date) × hour(date)` per-tenant; ячейка — и `count(*)`, и `sum(priceWithDisc)`, поскольку вендор не раскрыл, что агрегирует (PENDING) — давать обе, не гадать.
- Часовой пояс: в фикстуре `date` — 19 символов без суффикса пояса; трактовка как МСК в репо нигде не зафиксирована — перед расчётом подтвердить по спецификации WB Statistics и записать в контракт. Вендорский выбор «жёстко МСК, как датирует WB» (факт §7) — разумный дефолт и для PROXIMA (оценка).
- «Регион покупателя» у вендора соответствует `regionName`/`oblastOkrugName`/`countryName`; «логистические разрезы» вендор не раскрыл (PENDING) — у PROXIMA свой разрез по `warehouseName`/`warehouseType`, паритет оценить нельзя.
- WRITE / парсинг: нет, контур A. Зависимость от PENDING: **низкая** — capability полностью задана строкой заказа; PENDING только детали паритета (агрегат ячейки, значения статуса, легенда).
- Форма для лестницы: не отдельный экран, а виджет/контекст утренней сводки — «пик вчера пришёлся не на обычные часы / регион X выпал против нормы» (оценка).

**B2. Живая лента с обновлением ~10 минут.**
- Данные есть (те же строки; инкремент по `lastChangeDate`, лимит `orders` 10 по заголовку — `API-FACTS.md:11`), но режим near-real-time — другая форма продукта, чем утренняя сводка по дневному ряду; в лестнице M-00..M-05 не значится. Интерпретация автора «лента и дашборд не сойдутся» — аргумент **против** второй полосы в PROXIMA: одна фиксация «вчера» с `run_id` вместо двух рассогласованных чисел (оценка).
- Зависимость от PENDING: низкая. Ценность для лестницы низкая.

**B3. Статус заказа.** У PROXIMA только `isCancel`/`cancelDate` в заказах и связка с продажами по `srid` (`API-FACTS.md:24-25`); значения статуса вендора PENDING → **нельзя оценить** паритет.

**B4. Переключение кабинетов, роли «просмотр»/«редактор».** Платформенный слой (`platform/P2`, не читался); у PROXIMA мультитенантность заложена по определению проекта. Вне этого extract.
