## Зачем это бизнесу

Остатки - второй контур продукта после «утренней сводки»: знать, что товар кончается, до того как он
кончился (OOS), и сколько уже едет к клиенту. Эпик предпосылок M-06+ (PMM-63) включает именно их:
PMM-73 - AD об остатках (реестр AD-4 и формат загрузки), и от AD ждут PMM-86/PMM-87; E7 (прогноз спроса и
покрытие остатков) начинается с AD об остатках. Финансовый отчёт - деньги: маржа, комиссия, логистика,
хранение по строкам отчёта (юнит-экономика по SKU, CM-13), сегодня идёт только через мёртвый по спецификации
`reportDetailByPeriod`. Архивное видение M1 (`docs/archive/planning-m1/PRODUCT-VISION.md`, W4) ожидало
«избыток + 12-мес прогноз» от Finance API - рамка заменена лестницей, но потребность в финансовом разрезе осталась.

### Story S1: Дневной срез остатков по складам

As a Mike,
I want чтобы каждое утро после вчерашнего дня в БД ложился срез остатков по товару, размеру и складу,
So that OOS-логика M-06+ имела ежедневный ряд, а не разовые замеры.

**Acceptance Criteria (черновик):**

**Given** проба 02.09.2026 (API-FACTS, «Остатки (02.09.2026, OQ-13)»): 444 строки `data.items[]`
(`nmId`, `chrtId`, `warehouseId`, `warehouseName`, `regionName`, `quantity`, `inWayToClient`,
`inWayFromClient`), 76 608 B за 1.89 s при `limit 50`, лимит 1 запрос на окно
**When** проектируется запись
**Then** в БД - таблица дневного среза остатков с грейном **«товар × склад × день»**
(`fact_stock_daily`: `tenant_id`, `calendar_day` МСК по AD-7, `nm_id`, `chrt_id`, `warehouse_id`,
`warehouse_name`, `region_name`, `quantity`, `in_way_to_client`, `in_way_from_client`, `run_id`,
`evidence_sha256`); пустые `warehouse_id`/`region_name` - литеральные значения (видимая группа,
не скрытая - шаблон AD-19); строка среза = размер × склад; соответствие `chrtId` среза и `ChrtID`/`SizeName`
CSV истории - UNKNOWN до сверки (U3)

**Given** модель прогона AD-3
**When** job `stocks` создаёт прогон `kind = stocks_snapshot`
**Then** версия дня по `run_id`, view `_current` по правилу AD-3; удаление - транзитивно `delete_run.py`;
каждый день - один запрос (лимит 1 на окно - заголовок 02.09); при 429 - ожидание по `X-Ratelimit-Retry`,
≤ 3 повторов (NFR1); пагинация по `offset` НЕ строится до закрытия U2 (по пробе один ответ покрывает кабинет)

**Given** гейт и реестр (AD-4)
**When** `make verify`
**Then** `analytics.stocks_report_warehouses` добавлен в `registry.ts` c `limitPerMinute: 1` (из замера,
не из зеркала спецификации - PRD §4.0); гейт `verify_wb_client.py` обновлён синхронно (S3-модель ниже);
фикстуры - обезличенные (`anonymize_fixture.py`), ≤ 200 КБ; тесты - на `FixtureTransport`, сеть запрещена;
RLS, гранты и политики - по шаблону AD-11 в той же миграции (новый `NNN+1_snake.sql`, additive-only,
`verify_migrations.py`)
**And** Mike выполняет одно действие: `make verify` - гейт реестра с пятью эндпоинтами зелёный

**Что эпик тянет за собой.**

| Слой | Цена |
|---|---|
| Миграции | минимум 2 новые `NNN+1_snake.sql` additive-only (срез остатков + stg/promote истории CSV), с самопроверкой `verify_migrations.py`; нумерация - целевая, вторая мержащаяся ветка перенумеровывает (AD-14) |
| Роли | новые таблицы - гранты и политики в тех же миграциях по шаблону AD-11 (collector + janitor; при появлении читателей M-06+ - отдельные SELECT-гранты; webapp гранта не получает, AD-9) |
| Реестр и гейты | правка `registry.ts` + синхронная правка `verify_wb_client.py` («ровно четыре» → «ровно N») - осознанное изменение гейта в PR с источниками лимитов; allowlist-политика AGENTS.md соблюдается тем же PR |
| Время утреннего прогона | +1 запрос среза (окно лимита неизвестно, U2/U6) и - в понедельник - create/status/file CSV (< 65 с готовности, но общий бюджет окна `TimeoutStartSec` растёт); замерить на стенде репетиции до включения в цепочку; в цепочку `morning_run.sh` не входит до решения (шаблон CR к AD-6 для воронки) |

| Фикстуры | новые обезличенные фикстуры ≤ 200 КБ (D15); CSV остатков содержит реальные названия товаров - обезличивание обязательно (факт 12) |

**Предлагаемый порядок историй.**

1. **S1** срез остатков - самодостаточен: один запрос в день, поля известны, схема хранения ясна; закрывает
   главный разрыв «остатков нет в фактах лестницы».
2. **S2** CSV-история - после S1: переиспользует его таблицу и механику Epic 3; тест глубины (U1) -
   одной пробой в Step 0 истории, до кода.
3. **S3** реестр+гейт - «одной строкой» внутри S1 (правки реестра и гейта едут с первым новым
   эндпоинтом); выделяется отдельной историей в черновике, чтобы изменение гейта было видно приёмке
   отдельно и не пряталось в коде S1.
4. **S4** разведка финансового - независима от S1-S3, может идти параллельно (это одна проба с
   сервера + раздел в API-FACTS); S5 (если будет) - отдельное решение после S4.
