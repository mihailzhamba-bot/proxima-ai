## E6 (кандидат). События и диагноз отклонения по SKU - CM-10 → FR-36

Цель: каждый активный SKU ежедневно описан рядом событий (цена и скидка из строк заказов, доля склада, появление/исчезновение в воронке; позже - отзывы и реклама), а просадка по SKU объясняется только зафиксированными событиями (fail-closed). Контур историй:

1. Событийный ряд по nmId и дню из уже собранных строк заказов (`priceWithDisc`, `spp`, `warehouseName`) - таблица `fact_sku_event_daily` с `run_id`, удаляется прогоном.
2. Норма SKU по правилу D21 (медиана 14 полных дней по nmId), `insufficient` при истории меньше 14 дней, норма 0 без деления (правило FR-31/FR-32).
3. Просадка SKU против собственной нормы и связь с событиями; недельный профиль проверяется на backtest (D21 сделан на кабинетном ряду).
4. Диагноз из событий: главная причина и альтернативы только из ряда; выход - строка аномалии FR-25 с `source_refs`.
5. Расширение ряда событиями отзывов (после CM-11) и рекламы (после CM-4) - отдельные истории при появлении источников.

Гейт входа: D-решение по M-06 + SPEC; гейт приёмки: backtest на истории кабинета и сверка диагноза с фактом (SM-8, петля FR-18).

## E7 (кандидат). Прогноз спроса и покрытие остатков по SKU - CM-9 → FR-37

Цель: прогноз спроса по SKU на 30/60/90 дней, покрытие остатков в днях, рекомендация к закупке с количеством и датой; компоненты расчёта названы и видны (скорость и окно, сезонная поправка и источник, срок поставки, страховой запас); дни отсутствия товара исключены из обучения. Контур историй:

0. AD об остатках: включение `stocks-report/wb-warehouses` (снимок, лимит 1 запрос на окно) и `STOCK_HISTORY_DAILY_CSV` (дневная история, unpivot по датам) в реестр AD-4; allowlist; глубина `currentPeriod` назад (OQ-13).
1. `fact_stock_daily` по SKU × склад из снимка и CSV, `run_id`, обратимость.
2. Детерминированный baseline: скорость продаж (медиана 14 для тревоги, среднее 28 без OOS-дней для объёма), покрытие в днях, дефицит `max(0, target − stock)`.
3. AD ML-платформы (OQ-11): версии моделей, входы по `run_id`, SourceRef модели, backtest на фикстурах.
4. Первая модель интермиттентного спроса с конформными интервалами; rolling-origin backtest, метрика WAPE/MAPE зафиксирована до эксперимента; в сводку только при победе над baseline (SM-8).
5. Рекомендация к закупке (количество, дата, ссылка) как решение FR-5/FR-16 со сверкой через горизонт (FR-18); ручные переопределения из паспорта (CM-19, путь ввода OQ-8).

Гейт входа: D-решение + AD об остатках + AD ML-платформы; приёмка: ошибка прогноза на backtest ниже baseline, сверка через горизонт записана.

## E8 (кандидат). Сигналы эффективности рекламы - CM-4 → FR-38

Цель: ежедневные признаки потери рекламного бюджета по кампании и SKU как решения с ожидаемым эффектом; изменение кампаний система не выполняет никогда. Контур историй:

0. READ-токен категории «Продвижение» на VPS; разведка по образцу API-FACTS (`/adv/v1/upd`, `/adv/v1/payments`, `/adv/v0/normquery/stats`, `/api/advert/v2/adverts`, `/adv/v3/fullstats`); allowlist по полному пути с явным запретом GET `/adv/v0/start`, `/pause`, `/stop`, `/delete`.
1. `fact_advert_daily` и `fact_advert_cluster_daily` с `run_id`.
2. Семь сигналов S1-S7 (расход без заказов, доля рекламных расходов выше цели двумя способами с показом расхождения, конверсия ниже нормы, реклама на товар без остатка после E7, проигрышные кластеры, каннибализация) - пороги как значения конфига с источником и датой.
3. Оценка потерь в рублях с методикой и `source_refs`; «сэкономленный бюджет» без методики не публикуется; правило «расход не суммируется дважды» с финотчётом.

Гейт входа: D-решение + токен + разведка; приёмка: сигналы на живых данных с SourceRef, ноль write-вызовов (гейт `verify_wb_client.py`).

## E9 (кандидат). Поисковая видимость своих карточек - CM-12 → FR-39

Цель: ежедневно по своим ключевым запросам частота, позиция, видимость, добавления в корзину и заказы; сигнал потери позиции против собственной нормы SKU (без сравнения с конкурентами). Контур: разведка `search-report` на токене «Аналитика» (лимиты по спецификации, живой проверки не было; охват 30/100 запросов без/с «Джем»); `fact_search_daily`; норма по запросу; сигнал как правило с источником и датой (FR-20 не строится - значение конфига). Гейт входа: D-решение + разведка.

## E10 (кандидат). Рейтинг и отзывы как события - CM-11 → FR-40

Цель: падение рейтинга к собственной норме (на токене «Аналитика» через метод рейтинга товара) и поток отзывов как события для диагноза; черновики ответов только с человеком в контуре; публикация - никогда. Контур: событие рейтинга; после токена «Вопросы и отзывы» - новый негативный отзыв и возраст неотвеченного (< 30 дней); ПДн покупателей и провайдер LLM - по OQ-15 до первой истории. Гейт входа: D-решение + OQ-15 + токен.

## Что не входит ни в один кандидат (PRD §5)

Любая запись в WB; скрейпинг публичных страниц и внешних платформ; платные внешние источники как обязательная зависимость; автоисполнение решений; сравнение с конкурентами по поисковой выдаче; CM-18 (габариты) - заблокирован отсутствием источника.

## Поправки 03.09.2026 (после сверки с дропом и ресёрчем)

**E6, источники.** Черновик `event-diagnosis/SPEC.md` из дропа строит событийный слой на четырёх новых снапшотах - цены через `discounts-prices-api`, остатки, реклама, отзывы. PRD §12 по CM-10 говорит обратное: новых источников не требуется, цена и скидка берутся из `priceWithDisc` и `spp` строки заказа, склад - из `warehouseName`. Канон - PRD. Снапшоты рекламы и отзывов перенесены в E8 (CM-4) и E10 (CM-11), где токен нужен и так. Именно поэтому E6 идёт первым, хотя по баллу первый E7.

**E6, что взято из дропа сверх PRD.** Правило соответствия класса события метрике: отклонение показов не может быть объяснено изменением цены, потому что цена влияет на конверсию, а не на показы. Без этого правила диагноз вырождается в перечисление того, что было в тот день. Второе: исход «причина не найдена» записывается явно, а не отсутствием строк - пустой список и отсутствие диагноза разные состояния. Третье: снапшот хранит состояние, а не разницу, иначе смена порога делает пересчёт невозможным. Четвёртое: признак полноты дня ложится на существующую `quality_check_results` из миграции 007, новая таблица не нужна, а имена складов сводит существующая `dim_warehouse_map` из миграции 004.

**E7, ограничения ресёрча.** Минимальная длина истории для дневного ряда SKU не найдена ни в одном источнике и решается только собственным backtest - это блокирующая неизвестность, а не деталь. Дни отсутствия товара исключаются из обучения и из расчёта скорости, иначе прогноз систематически занижен. Модель попадает в сводку только если побеждает детерминированный baseline на rolling-origin backtest по метрике, зафиксированной до эксперимента. Честный контраргумент, который стоит держать перед глазами: для коротких разреженных рядов по SKU машинное обучение не даёт автоматического выигрыша, и вероятный исход - медианный baseline окажется почти так же хорош.

**Новые эпики.** Для CM-13, CM-14 и CM-17 в этом файле были только строки таблицы порядка без разделов. Эпики заведены в Jira: PMM-66 (юнит-экономика), PMM-70 (клиентский отчёт), PMM-71 (лента заказов и тепловая карта).

**Кандидаты вне очереди.** Двенадцать кандидатов реестра - CM-1, CM-2, CM-3, CM-5, CM-6, CM-7, CM-8, CM-15, CM-16, CM-18, CM-19, CM-20 - заведены задачами в эпике PMM-72, каждая с баллом, статусом и блокером. Отдельными эпиками они не заводились: двенадцать эпиков без работы это шум.
