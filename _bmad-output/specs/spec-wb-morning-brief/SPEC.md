# Утренняя сводка WB с отклонениями от нормы

## Why

Боль и срок. Владелец кабинета WB (в сентябре - Mike, кабинет ИП Амировой) каждое утро вручную смотрит кабинет, чтобы понять, упали ли продажи; система должна сама показывать в веб-морде «вчера против нормы». Код-фундамент (collector, control-plane, webapp) написан, но сбор данных не запущен, а WB Statistics отдаёт историю скользящим окном ~6 месяцев: март 2026 выпадет из окна в сентябре, поэтому бэкфилл нельзя откладывать. Роадмап M1 заменён лестницей M-00..M-05; M-00 (разведка API) выполнен 30.08.2026; к 30.09.2026 должна работать M-03.

## Capabilities

- **CAP-1** [M-01]
  - **intent:** Система ежедневно забирает из WB Statistics заказы и продажи кабинета за прошедшие дни и накапливает дневной ряд.
  - **success:** Три дня подряд без ручного вмешательства в БД есть ряд за каждый день; повторный прогон за тот же день не создаёт дублей.
- **CAP-2** [M-01]
  - **intent:** При подключении кабинета система загружает всю доступную историю (сейчас с 01.03.2026) до того, как окно WB её вытеснит.
  - **success:** Недельные суммы в БД совпадают с фикстурами 30.08: W10 = 649 заказов / 700 860 ₽, W35 = 225 / 263 089 ₽.
- **CAP-3** [M-01]
  - **intent:** Пользователь на `/brief` видит, до какой даты есть данные и когда они обновлялись.
  - **success:** Строка статуса с датой и временем; при отсутствии сбора более 24 часов - явное предупреждение вместо цифр.
- **CAP-4** [M-02]
  - **intent:** Система каждое утро считает норму кабинета: медиана по фиксированному окну 14 календарных дней перед оцениваемым днём, сам день в окно не входит (AD-8), отдельно по заказам без отмен и по выручке. День окна без версии дневного ряда уменьшает `sample_days`; при `sample_days < 14` норма получает статус `insufficient`, а пропуск остаётся виден.
  - **success:** На фикстурах 30.08 для 29.08 норма = 34.5 заказа и 34 595 ₽ (детерминированный тест, `glossary.md`).
- **CAP-5** [M-03, граница сентября]
  - **intent:** Каждое утро на `/brief` - вчерашний день против нормы в процентах по заказам и выручке.
  - **success:** Утром 30.09.2026 сводка за 29.09 с цифрами, совпадающими с кабинетом WB; сводка приходила каждое из 7 предыдущих утр без вмешательства.
- **CAP-6** [M-01b, фон]
  - **intent:** Система копит воронку (открытия → корзина → заказы → выкупы, слова по `glossary.md`) по nmId: async CSV и v3 sales-funnel ежедневно.
  - **success:** К 27.10.2026 в БД N недель дневной воронки по каждому активному nmId, где N = (27.10 − дата первого успешного `funnel_v3` на сервере) / 7 (SM-7). Цель «8 недель» требовала старта 01.09 и снята решением 3а (D25): при релизе воронки к 23.09 выходит N ≈ 5. «Активный nmId» = distinct `nmId` из `stg_wb_orders_latest` за последние 30 дней.
- **CAP-7** [M-04, октябрь]
  - **intent:** Система отделяет сигнал от шума и ранжирует отклонения по деньгам в разрезе SKU и категории.
  - **success:** Список аномалий отсортирован по потерянной выручке; дни в пределах шума в список не попадают.
- **CAP-8** [M-05, октябрь]
  - **intent:** К каждой аномалии система даёт гипотезу причины и что проверить, с источником каждой цифры.
  - **success:** У каждой аномалии в сводке не меньше одной гипотезы с проверкой и SourceRef; цифр без источника нет.

## Constraints

- Источник данных - только официальный WB API кабинета, только READ-эндпоинты; ручная выгрузка отклонена. Лимиты и мёртвые методы - `API-FACTS.md` (sales и reportDetail 1/мин, orders 10/мин, v3 3/мин; nm-report v2 снят; окно Statistics ~6 мес).
- Канал доставки - существующая веб-морда `services/webapp`, экран `/brief` (точка встраивания - `WEB-STATE.md` §8); не Telegram, не почта.
- Без авторизации и ролей в этом квартале; auth-зона webapp и `services/control-plane/src/proxima/` заморожены до октября.
- Тесты только на фикстурах; живой WB API - только когда без него никак; каждый новый ответ при первом прогоне сохраняется как фикстура (канон - VPS `~/signal-inputs/fixtures/wb-api/` + S3, в git не входит).
- Обратимость данных: каждая запись помечена `run_id`, запись идемпотентна, результаты одного прогона удаляются целиком.
- Одна модель данных на много кабинетов (`tenants`, RLS); сентябрь - один tenant (ИП Амирова), второй после M-03.
- Норма - медиана по фиксированному окну 14 календарных дней перед оцениваемым днём, сам день исключён (AD-8), по кабинету целиком; пересчёт каждое утро. Метрика тревоги - заказы без отмен, выручка (finishedPrice по продажам) справочно; отклонение = вчера к медиане в процентах. Конвенции медианы, округления денег и отклонения - `glossary.md` раздел «Конвенции расчёта» (D27).
- Переиспользовать через ревью, не переписывать: детектор нормы `origin/mihailzhamba-bot/pmm-20-scn-001-…`, писатель дневного ряда `origin/mihailzhamba-bot/pa41-full-w2-phase3`, контракты сигнала `origin/mihailzhamba-bot/pmm29-contracts`, провайдер `/brief` `origin/ai/pa-50` (`MIGRATION-GAPS.md` §4). Три `010_*.sql` перенумеровать при мерже; миграции additive-only с self-checksum.
- Среды: один VPS; боевая база + `proxima_test` для тест-запусков; OpenHands-сандбокс только к `proxima_test`.
- Сервер для агентов - только чтение; деплой только после явного «деплой» от Mike с записанным планом отката; секреты не покидают VPS.
- Единица работы = один сеанс OpenHands + один связный PR + один результат, который Mike проверяет одним действием.
- Расписания сбора на сервере нет и не было; первая единица M-01 (расписание + бэкфилл) уходит в OpenHands не позже 08.09.2026.
- База регрессии до автотестов - `WORKS-TODAY.md` (33 пункта), прогоняется целиком перед каждым релизом.

## Non-goals

- Авторизация, роли, многопользовательский доступ - не в этом квартале.
- Ozon и любые источники кроме WB API кабинета.
- Второй кабинет до завершения M-03.
- Telegram, почта, push как канал сводки.
- Воронка в утренней сводке в сентябре (копится фоном, в сводке - октябрь).
- Переписывание веб-морды и `bmad-ux`.
- Torgstat и любая браузерная автоматизация в runtime.
- Восстановление списанных веток `pa-9`, `stash/pa-27-snapshot`; `now-orchestrator` вне лестницы.
- Любая запись в WB (цены, остатки, контент) - никогда.

## Success signal

Утром 30.09.2026 Mike открывает `/brief` и видит строку вида «29.09: 31 заказ против нормы 34.5 (−10 %), выручка 33 800 ₽ против 34 600 ₽», статус «данные до 29.09, обновлено сегодня 06:xx»; цифры совпадают с кабинетом WB, и та же сводка приходила каждое утро всю предыдущую неделю без ручного запуска.

## Assumptions

- Дневной квоты async-отчётов WB хватает на наш один отчёт в день при внешнем потребителе того же токена (D20).
- v3 sales-funnel: 201 nmId = 11 вызовов в день при лимите 3/мин - допустимая нагрузка.
- Референс тестов - `make verify` на маке (Homebrew PG16); зона OpenHands на VPS получает uv и node через `.openhands/setup.sh`.

## LOOP pilot - принятое переопределение от 13.09.2026

Источник: план Mike в чате 13.09.2026 и `docs/exec-plans/active/loop-pilot.txt`.
Это отдельный датированный слой пилота поверх сентябрьской лестницы. Ранее
утверждённые решения и история сохраняются. Незамерженный PR #134 не становится
принятым архитектурным решением по факту этой реализации.

Для пилота снят прежний запрет на auth, личные роли и очередь сотрудника.
BetterAuth проверяет сессию на сервере, включая истечение и отзыв; membership
выдаётся оператором отдельно от регистрации. Postgres-режим не может отключить
эту проверку. Кабинет задаётся сервером; сотрудник читает и изменяет только свои
задачи. Mike подтверждает действие, сотрудника, срок, измеримую цель и горизонт.
Решение и задача фиксируются одной транзакцией; повтор, включая новый ключ той же
аномалии, возвращает прежнюю задачу. Подтверждение привязано к просмотренному
snapshot. Блокер, выполнение с evidence, отмена и наблюдение имеют разные записи.

Порог пилота -30 процентов закреплён в detector/threshold.toml с источником этого
решения и датой 2026-09-13. Он предварительный, не результат ретрокалибровки.
Существующая медиана календарных дней D-14..D-1, денежная арифметика и SourceRef
сохраняются. Stale/insufficient/нет источника скрывают неподтверждённые показатели.
Рабочий бриф не содержит редакционных fixtures. Первый разбор имеет тип
`deterministic-pilot-v1`: факты, гипотеза, альтернативы, неизвестные и проверка;
он не объявляется ответом LLM или canonical `diagnosis`/`diagnosis.draft.v1`.

Отдельный `workflow_runs` не меняет закрытый collector_runs.kind. Решения, задачи,
события и наблюдения append-only для runtime; роль auth не пишет доменные решения.
Удаление исходного collector run оставляет решение и snapshot, связь становится
orphaned. Collector janitor не удаляет человеческую очередь. Выполнение не означает
достижение цели. Независимое наблюдение начинается после горизонта и сравнивает
orders/count или revenue/RUB того же SKU; категории и неподдержанные метрики дают
unknown. Достижение цели не доказывает причинный эффект действия.

Управляющий LOOP размещается на новом отдельном VPS: Paperclip, отдельный Hermes
Director, свой PostgreSQL и persistent Bridge. Simone исключён. Память, OAuth и
credentials существующего Hermes не копируются. Paperclip единственный scheduler
Director; Bridge хранит намерения, связь запусков, события и запрет поздней
публикации. Official hermes_gateway идёт через Bridge к Hermes. Отмена сначала
закрывает публикацию, затем явно останавливает Hermes и OpenHands; неподтверждённая
остановка остаётся cancelling. Unknown dispatch не повторяется автоматически.
OpenHands исполняет утверждённый шаблон; Harper сам запускает verify/build и
независимый review на точном SHA. Конечное состояние - готовый PR. Merge,
production deploy и покупка VPS требуют отдельного решения Mike.

Пакет: `infra/loop-control/OPERATIONS.txt`, `versions.lock.json`, `compose.yaml`;
код: `tools/loop/`. Telegram ingress использует отдельный bot token и allowlist,
сохраняет входящие команды и вызывает тот же Bridge. Eval Director сравнивает
на одинаковых задачах выбранные оператором модели; креды и сами model IDs не
выдуманы. Runtime-инструменты Director ограничены предложением утверждённой задачи;
терминал и cron отсутствуют в явном наборе. Тяжёлые сборки на управляющем VPS
запрещены. Логи ограничены, недостаток свободного диска блокирует dispatch.

Статус приёма: новый VPS/IP, отдельные credentials, image digests, runtime tool
inventory, самостоятельное ревью в runner, реальный Telegram/Director/worker
roundtrip и ежедневная эксплуатация проверяются отдельно. Локальные/Harper тесты
не означают live-готовность. Итоговые evidence и PR добавляются в handoff после
независимой проверки.
