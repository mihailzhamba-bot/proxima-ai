# Как вносить изменения

Правила для человека, который работает в этом репозитории рядом с конвейером агентов. Полный вход - `docs/operations/dev-onboarding.md`; права и запреты - `docs/agent-system/RULES.md`, `AGENTS.md`; роль аналитика - `docs/agent-system/roles/analyst-vladislav.md`. Решение о защите `main` и правилах - `DECISIONS.md` D34.

## Аккаунт и доступ

- Один человек - один аккаунт GitHub, включённая двухфакторная аутентификация. Общих и вторых аккаунтов нет.
- Право в репозитории - Write: ветки и PR. В `main` попасть напрямую нельзя: ветка защищена правилом `main-protected` (PR обязателен, одобрение владельца, зелёные проверки, force-push запрещён). Мерж делает владелец репозитория.
- В `git config` - настоящее имя и e-mail, привязанный к аккаунту GitHub, иначе коммиты не свяжутся с профилем:

```bash
git config user.name "Имя Фамилия"
git config user.email "адрес-из-GitHub"
```

## Ветка и PR

- Ветка от свежего `origin/main`: `feat/…`, `fix/…`, `docs/…`, `chore/…`; у аналитика - `analyst/<ключ-Jira>-<slug>`, например `analyst/PMM-58-data-quality`.
- Один PR - одна задача Jira, ключ в заголовке PR и в первом коммите. Маленький PR лучше большого: один результат, который владелец проверяет одним действием.
- Коммиты - по-английски с conventional-префиксом (`docs(analytics): …`, `feat(collector): …`), атомарные. Стейджить только свои файлы: `git add <files>`, никогда `git add -A`.
- До первого запроса ревью ветку можно перебазировать: `git fetch origin && git rebase origin/main`. После начала ревью - только `git merge origin/main`; force-push в ветку с открытым PR запрещён (ревьюер теряет контекст).
- PR заполняется по шаблону: что и зачем, результат `make verify`, DoD-аудит по семи пунктам, отметка `unreleased` для цифр.

## Проверка и мерж

1. CI зелёный: `verify` (make verify на Ubuntu с PostgreSQL 16) и `images` (сборка образов, миграции в контейнере).
2. Независимое ревью: агент-ревьюер (запускает владелец) или второй человек; ответы на замечания - в PR, не в чате.
3. Одобрение владельца репозитория; владельцы путей из `.github/CODEOWNERS` запрашиваются автоматически.
4. Мерж - merge commit (как во всей истории `main`); ветку после мержа не удаляем без явного решения.

## Локальная проверка

```bash
make install                      # зависимости + core.hooksPath=.githooks
PUPPETEER_SKIP_DOWNLOAD=1 make verify
```

Без локального PostgreSQL 16 шаг `pg-roundtrip` печатает `SKIP` и выходит с кодом 0 - миграции и db-тесты тогда проверяет только CI. Одна проверка: `npm --workspace @proxima/webapp exec -- vitest run src/tests/<file>`; Python - только через `uv run --python 3.14 --project services/control-plane --extra test pytest …`.

## Чего не делать

- Не править `.github/workflows/*`, `tools/verify_*.py`, `db/migrations/*`, `contracts/*.schema.json`, сгенерированные типы и замороженные зоны - это меняется владельцем или отдельным решением. Новые файлы-верификаторы (`tools/verify_shadow.py`) создавать можно.
- Не коммитить секреты, токены, полные фикстуры и реальные идентификаторы кабинета; `make secrets` в `make verify` это ловит, но лучше не доводить.
- Не делать живых вызовов WB API и ничего не писать на сервер без отдельного разрешения владельца.
- Застрял больше двух часов - написать владельцу, не буксовать молча.
